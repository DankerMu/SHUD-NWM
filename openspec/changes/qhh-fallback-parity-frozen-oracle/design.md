# Design

## D1 Frozen baseline = exact pre-#1413 text, as data

`tests/fixtures/legacy_qhh_fallback_pre_1413.sql` holds the single statement body from `git show 90dc4a7e:packages/common/forecast_store.py` (method `_fetch_latest_qhh_display_candidates`, the `self._fetch_all(cursor, f"""...""", (...))` statement), with the `{identity_sql}` placeholder line removed (identity=None is the only mode under test; it is the only brace pair in the body, and removing the line leaves `AND LOWER(h.source_id) = LOWER(%s)` directly followed by `AND h.cycle_time IS NOT NULL` — valid SQL) and nothing else altered — whitespace/comments included. Header comment (SQL `--`): provenance (commit `90dc4a7e`, method, issues #1413/#1414); "FROZEN parity baseline — never update alongside production SQL"; the two known divergences from production so nobody assumes the removed identity line is the only delta: (a) #1413 pushdown shape (the reason it exists), (b) #1442 surrogate-key river join — the frozen text joins `hydro.river_timeseries` on text identity columns and its candidate CTE has no `run_key` / `basin_version_key` / `river_network_version_key`; "if it stops executing, the schema moved under it (#1342) and the change that moved it must re-freeze or retire this oracle". The module constant `_LEGACY_FALLBACK_SQL = (Path(__file__).parent / "fixtures" / "legacy_qhh_fallback_pre_1413.sql").read_text(encoding="utf-8")` lives in `tests/test_display_coverage_residual_debt_integration.py` next to `_LEGACY_PUBLISH_SQL`. Rationale for a data file: 500 lines of SQL in a Python module invites reformatting and hides the "never edit" intent; a `.sql` file is diff-obvious.

Binding (positional, legacy order): `(forecast_store.QHH_LATEST_EXPECTED_HORIZON_HOURS, BASIN_ID, source_id, forecast_store.QHH_LATEST_SEARCH_LIMIT, list(forecast_store.MVP_STATION_VARIABLES), len(forecast_store.MVP_STATION_VARIABLES))` — with `identity=None` the legacy `*identity_params` collapses to nothing, so this is the call site's exact order. Using the production constants is deliberate: they are *inputs* shared by both sides (the new path binds the same names), not arithmetic; `QHH_LATEST_SEARCH_LIMIT` was already 1 at `90dc4a7e` (verified). `_fetch_all` sends a non-Mapping through `tuple(parameters)` for `%s` binding (`packages/common/forecast_store.py:2599-2603`) — the right path for the legacy tuple.

## D2 Parity helper and what "identical" means

The current heavy statement's final SELECT is `cr.*` (`packages/common/forecast_store.py:~1980`), and `cr` = `_QHH_LATEST_CANDIDATE_RUNS_SQL`, which since #1442 carries three columns the frozen text does not: `run_key`, `basin_version_key`, `river_network_version_key` (`forecast_store.py:264-266`). Nothing downstream pops them. So the comparison is a **projection with an asserted exclusion set**, never plain dict equality:

- `_NEW_ONLY_COLUMNS = frozenset({"run_key", "basin_version_key", "river_network_version_key"})`
- `_parity_pair(store, *, source_id=SOURCE_ID)` opens ONE `store._transaction()` (REPEATABLE READ, readonly — one snapshot), runs the new fallback then `store._fetch_all(cursor, _LEGACY_FALLBACK_SQL, legacy_tuple)`, and for each new row pops exactly `_NEW_ONLY_COLUMNS`, asserting `popped == _NEW_ONLY_COLUMNS` (each key present) and afterwards `set(new_row) == set(legacy_row)`. A FUTURE column added to the candidate CTE therefore turns the test red instead of silently widening the exclusion.
- Then `new_rows == legacy_rows` on `list[dict]` (column set + values + order).

Every state adds a non-vacuity guard so "equal" is never "empty == empty" (D3). The forced fallback is `monkeypatch.setattr(forecast_store, "_run_display_coverage_available", lambda _cursor: False)` as in the existing test, and it stays active in every parity test including the negative control.

## D3 States

- Station rows. `seed_issue_126_data` inserts **no** `met.met_station`, `met.interp_weight` or `met.forcing_station_timeseries` rows (those tables appear in `tests/integration_helpers.py` only in `_clear_issue_126_rows`). The parity module seeds them with a **private helper** (`_seed_station_coverage(connection)`), NOT by extending `seed_issue_126_data`: `tests/test_real_database_integration.py:209,274` run the shared seed twice on one session database and `_clear_issue_126_rows` never deletes `met.met_station` / `met.interp_weight` (only NULLs `grid_snapshot_id`), so shared station rows would PK-conflict there. Recipe: 1 `met.met_station` row (`basin_version_id = BASIN_VERSION_ID`, `geom` Point SRID 4490; DDL `db/migrations/000005_met.sql:47-57`), 6 `met.interp_weight` rows — one per `MVP_STATION_VARIABLES` entry, `model_id = MODEL_ID`, `source_id = SOURCE_ID` — and 12 `met.forcing_station_timeseries` rows (6 variables × `VALID_TIME_1`/`VALID_TIME_2`, `basin_version_id = BASIN_VERSION_ID`, `forcing_version_id = FORCING_VERSION_ID`). This matches the seed's `forcing_version.station_count = 1` (`integration_helpers.py:272`) so both the `station_count = expected_station_count` gate and `HAVING COUNT(DISTINCT variable) = %s` fire; with fewer than all 6 variables the common-window columns (`station_valid_time_start/end`, the jsonb `valid_time_start/end`) stay NULL, so the full recipe is required.
- (i) covered: seed + `_seed_station_coverage`. Non-vacuity: `len(rows) == 1`, `station_count == 1`, `station_variable_coverage` non-empty, `station_valid_time_start is not None`, `segment_count > 0`.
- (ii) NULL identity: over the test's own autocommit `_connect()` connection (NOT `store._transaction()`, which is `readonly=True`, `forecast_store.py:~2656`), insert a second forecast run `f"{ISSUE_126_PREFIX}_forecast_run_nullfv"` (same model/basin/source, `status='parsed'`, `forcing_version_id=NULL`, `cycle_time = CYCLE_TIME + 6h`, start/end shifted alike, `run_manifest_uri` supplied — it is NOT NULL per `000006_hydro.sql:16`) so it becomes the single candidate (`LIMIT 1`, `ORDER BY cycle_time DESC`); seed river rows for it via `insert_river_timeseries_dual_written` (needs only hydro_run / basin_version / river_network_version / river_segment authority rows, no forcing version) — ≥2 segments × ≥2 valid_times inside its window. `GREATEST`/`LEAST` ignore NULLs so `display_start/end` bind non-NULL; only `scan_forcing_version_id` is NULL → guard disabled. Non-vacuity for THIS state is that station rows for `FORCING_VERSION_ID` exist in the snapshot (state (i)'s helper ran) and are correctly excluded by the `cr.forcing_version_id = fst.forcing_version_id` NULL-join on both sides: assert `rows[0]["forcing_version_id"] is None`, `station_count == 0`, `station_variable_coverage == []` on BOTH sides, and `segment_count > 0`.
- (iii) empty header: both sides with `source_id="no_such_source"` → both `[]`. Short-circuit itself (no heavy statement) stays pinned by the unit tests.
- (iv) negative control (forced fallback still active): `monkeypatch.setattr(forecast_store, "_QHH_LATEST_CANDIDATE_RUNS_SQL", forecast_store._QHH_LATEST_CANDIDATE_RUNS_SQL.replace("INTERVAL '1 hour'", "INTERVAL '1 second'"))`, assert the text changed, then on state (i) assert the projected `new_rows != legacy_rows`. Why `'1 second'`: `QHH_LATEST_EXPECTED_HORIZON_HOURS = 168`, cycle `2026-05-03T00:00Z`, the seed's run and forcing windows both end at `VALID_TIME_2 = 02:00Z`, so `LEAST(h.end_time, fv.end_time, cycle + 168 min = 02:48Z)` is unchanged — a `'1 minute'` mutant is inert. With `168 s` the end (`00:02:48Z`) falls below `display_start_time` (`01:00Z`): `display_end_time` itself differs in `cr.*` and the river window empties (`segment_count` → 0). `_qhh_latest_candidate_runs_sql` reads the module global at call time (`forecast_store.py:325-328`), so the monkeypatch reaches the executed statement.

## D4 Why not compare against FAST again / why not hand-computed expectations

Hand-computed coverage arithmetic (issue alternative) drifts on its own and does not match the spec wording. FAST is same-idiom. The frozen statement is the spec's literal baseline.
