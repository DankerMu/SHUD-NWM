The gate's first half (zero in-window legacy-routed versions by `cycle_time`, the predicate the spec

- **The `end_time` cohort.** 760 legacy-routed versions still have `end_time` inside the window until
  2026-10-16. After this code is deployed, a coverage refresh that re-selects a run of such a version
  whose river facts are still in window rewrites the row with `station_count = 0` (the upsert guard in
  `display_coverage.py` protects only the river side). No code guard is added for this (it is moot from
  2026-10-16). Deploying before that date means accepting it; that choice is the owner's.

## D3 — Refusal vocabulary: deleted, writers write narrow

`LEGACY_STORE_REFUSED_CODE`, `LegacyForcingStoreRefusedError`, `legacy_store_refusal_message`,
`REASON_APPLY_LEGACY_STORE_REFUSED`, the producer's `_refuse_legacy_routed_forcing_version` and its
`except` arm, both refusals in `forcing_domain_handoff_apply.py`, and the autopipeline's mapping of that
code to `skipped` are removed. A formerly legacy-routed version is from now on treated exactly like any
other version — deliberately. For the handoff writer that means three outcomes, none new:
(1) checksum unchanged or NULL → rows are written to the narrow table through the unchanged
compressed-chunk write guard (the cure, per `I9-1988.md` D0); (2) a regenerated package with a different
checksum hits `_upsert_forcing_version`'s `ON CONFLICT … WHERE checksum IS NULL OR checksum =
EXCLUDED.checksum` and fails with `REASON_APPLY_FORCING_VERSION_CONFLICT` (tick failed, retried) —
the same as for any version; (3) a target inside a compressed narrow chunk → BLOCKED → declined.
`_legacy` rows of a rewritten version are orphans until 8.2 drops the table, and its column value stays
`legacy`: nobody maintains the column after this cut, which is harmless to 8.2 (its predicate is
`cycle_time`).

`openspec/specs/hypertable-compression/spec.md` names `HANDOFF_APPLY_LEGACY_STORE_REFUSED` as a
non-failing skip code; the change's `specs/hypertable-compression/spec.md` delta amends that scenario.

The residency observer loses its `legacy_store_refused` class: such a run is reported like any other
failed run. `openspec/specs/autopipe-parse-failure-residency/spec.md` is amended by the delta in this
change (`specs/autopipe-parse-failure-residency/spec.md`); `docs/runbooks/production-ops/
parse-failure-residency-alert.md` lines that describe the class are corrected.

## D4 — #2511 option (a): the version restriction stays on the hypertable

Deleting the legacy leg would leave the QHH fallback and display-coverage narrow templates with the
version restriction only on `fv.forcing_version_id`, i.e. not on the fact table; the module docstring of
`tests/test_qhh_latest_fallback_pushdown.py` records the 633 s precedent for a scan with no literal
predicate on the hypertable. Therefore:

- Both narrow templates (the QHH fallback in `forecast_store.py`, the station leg in
  `display_coverage.py`) gain, next to the existing `scan_forcing_version_id` guard and in the same
  fold-away form, `(%(scan_forcing_version_key)s IS NULL OR fst.forcing_version_key =
  %(scan_forcing_version_key)s)`.
- `scan_forcing_version_key` is bound everywhere `scan_forcing_version_id` is: projected as
  `fv.forcing_version_key` by the candidate CTEs and header SELECTs, added to `forecast_store`'s
  `parameters.update(...)`, to `display_coverage._SCAN_PARAM_KEYS` (the `--all` form binds NULL through
  `dict.fromkeys`) and to its `params.update`. Hand-written parameter dicts in tests and helpers gain the
  key. The id comes from `h.forcing_version_id`, the key from the LEFT-JOINed `fv` row; a non-NULL id
  with a NULL key is excluded by the foreign key in `db/migrations/000006_hydro.sql` plus the key being a
  NOT NULL identity. Were it to happen the predicate folds away: results stay correct, only the push-down
  is lost. The fast path scans no fact table and needs no binding.
- `test_scan_pushdown_predicates_present_in_both_sample_ctes` asserts the `fst.forcing_version_key`
  predicate **inside the station CTE**; `test_display_coverage_refresh.py`'s assertion that went red with
  the legacy leg is re-pinned to `fst.forcing_version_key`, not to `fv.`. Mutation: removing the new
  predicate from either template turns its test red.

## D5 — Smoke reset and the `_legacy` foreign keys

`_legacy` has FKs to `met.forcing_version` and `met.met_station` without `ON DELETE CASCADE`, so a smoke
database that still holds legacy facts would fail the later `DELETE FROM met.forcing_version` once the
routed legacy DELETE leg is gone. `bd06c6ddc` removed river's legacy delete from this script outright
(river's legacy table had no such FK problem to leave behind), so forcing cannot mirror it. Decision:
`scripts/reset_qhh_smoke_db.py` keeps one bare statement outside the renderer,
`DELETE FROM met.forcing_station_timeseries_legacy WHERE forcing_version_id = ANY(%s)`, executed only
when `to_regclass('met.forcing_station_timeseries_legacy') IS NOT NULL`, with ids selected without the
routing column, and a comment saying it is removed with 8.2. The census (D7) gets one name-only
exemption row for it, also marked for 8.2.
