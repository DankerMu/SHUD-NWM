## Context

Issues #1446 and #1725 — the display coverage refresh write point. A silent overwrite that destroys production display coverage is a data-loss surface: fixture level `expanded`, repair intensity `high`. Repo facts (fixture review, revision 1): both `refresh_run_display_coverage` (`packages/common/display_coverage.py:652-660`) and the batch worker `refresh_one` (`:731`) execute the shared `_refresh(conn, run_id)`, whose single statement `_REFRESH_SQL` (`:647`) is an `INSERT … ON CONFLICT DO UPDATE` — the scan count is not observable before the write; `_refresh(conn, None)` is the all-runs form pinned by `tests/test_display_coverage_refresh.py:104`; `refreshed_at` is bumped by the upsert, so a run that is never written stays in `_stale_run_ids` (`:764-779`) and is rescanned by the cron `--all --skip-fresh` loop (`scripts/node27_autopipe_cron.sh:229`) every tick; the CLI `report = {..., **counts}` (`scripts/node27_refresh_coverage.py:122`) returns 0 unconditionally and has no exception handling around `--run-id` (`:124-125`); the autopipeline never consumes the `--all` dict and treats a non-zero `--run-id` rc as `refresh_failed_rc{rc}` with outcome still `ingested` (`scripts/node27_autopipeline.py:2089-2099`); `tests/test_display_coverage_parallel.py:54` asserts the exact three-key dict; `tests/test_display_coverage_refresh.py:82,101` pin `_REFRESH_SQL`'s presence/absence in the statement sequence; the runbook prohibition is at `docs/runbooks/current-production-ops.md:126-128`. The protected population is runs whose `hydro.river_timeseries` rows carry `run_key IS NULL` (pin test `tests/test_river_ts_read_path_surrogate_keys_integration.py:779-785`), not a `hydro_run.parsed_at` cohort.

## Goals / Non-Goals

**Goals**: no refresh path (single-run, batch, all-runs) can zero a populated coverage row by accident; the explicit zeroing path still exists; the CLI reports a refusal as a structured, non-traceback outcome; both worker paths of the batch refresh provably isolate one failure.

**Non-Goals**: #1341 read-path switch; #1342 column drop; legacy key backfill/drain policy; other #1442 text-identity consumers; any production change for #1725 beyond the fourth summary key; station-side scanning.

## Decisions

### D1 (#1446) — the guard is the upsert's own `WHERE`, at the shared `_refresh`
`_REFRESH_SQL` gains a `force` parameter and a conditional update clause: `ON CONFLICT (run_id) DO UPDATE SET … WHERE %(force)s OR EXCLUDED.segment_count > 0 OR hydro.run_display_coverage.segment_count = 0`. A populated row whose fresh scan is empty is therefore skipped atomically inside the single statement — no read-before/rollback dance, no race with a concurrent refresh, and the all-runs form `_refresh(conn, None)` inherits the protection for free (its skipped rows are simply not returned). The three "unchanged" claims from revision 0 are withdrawn: `_REFRESH_SQL` changes, and `tests/test_display_coverage_refresh.py:82,101` keep pinning its presence in the sequence. Refusal is decided **only** from the statement's own outcome, never from the absence of a result row: `_refresh` returns a small `RefreshOutcome(refreshed: list[str], refused: list[str])` where, in single-run mode, `refused = candidates − returned`, `candidates` being the run ids that actually reached the upsert (the header row `_refresh` already fetches at `:628-636`). This is exact, not heuristic: the `coverage` CTE is `FROM candidate_runs` left-joined to the river rollup (`:502`), so a candidate always produces one upsert row, and "reached the upsert but absent from `RETURNING`" can only mean the `WHERE` skipped it — no extra probe is needed. The all-runs form `_refresh(conn, None)` runs no header query (`:628`, pinned by `tests/test_display_coverage_refresh.py:110`) and therefore has no candidate set: it returns `RefreshOutcome(refreshed, refused=[])` — it **protects** (skipped rows are simply not returned) but does not classify; refusal accounting exists only where a run id is known. The early return at `display_coverage.py:635-636` (no header row → not a candidate → `_REFRESH_SQL` never runs) yields `RefreshOutcome([], [])`, so a non-candidate run that still owns an old populated coverage row stays "no-row"/`skipped`/`no_coverage_row` exactly as today (pinned by `tests/test_display_coverage_refresh.py:93-101`, updated to the new return type). A run that reached the upsert and was not returned can only have been skipped by the `WHERE` (existing `> 0`, new `= 0`, no force), so `refresh_run_display_coverage` fetches `existing_segment_count` with one `SELECT` for the message and raises `DisplayCoverageRefreshRefused(run_id, existing_segment_count, advice)`; nothing was written, the transaction is rolled back before raising for hygiene. `refresh_one` in the batch inspects `RefreshOutcome.refused` directly (no exception round-trip) and returns a `"refused"` outcome that the summary counts. Whole-row skip is deliberate: the `DO UPDATE` sets 16 columns (`:552-567`) and a skipped row keeps its station-side columns and `refreshed_at` too. Accepted because the protected cohort is finished, pre-cutover runs whose station inputs no longer change; the freeze ends when the identity backfill (#1408) restores their keys and the next refresh succeeds. Rejected: CLI-only legacy probe (library stays dangerous); read-before/upsert/rollback (extra statement on every run, and a race window); per-column `CASE` protection (would need a refusal signal the `RETURNING` clause cannot express).

### D2 (#1446) — `force` is a keyword, `--force` is the CLI spelling; the CLI never tracebacks on refusal
`_refresh(conn, run_id, *, force=False)`, `refresh_run_display_coverage(connection, run_id, *, force=False)`, `refresh_all_run_display_coverage(..., force=False)`; `scripts/node27_refresh_coverage.py --force`. `--run-id <legacy>` without force exits 3 and prints one stderr line `DISPLAY_COVERAGE_REFRESH_REFUSED run_id=<id> existing_segment_count=<n> advice=<text>`; `--all` prints the four-key report on stdout and still exits 0. The cron loop never passes `--force`.

### D3 (#1446/#1725) — batch summary gains an additive `refused` key
`refresh_one` maps `RefreshOutcome.refused` to a `"refused"` outcome (committed, nothing written) that `refresh_all_run_display_coverage` counts under `refused`, before and independent of the generic `except Exception` arm; the return dict becomes `{"refreshed", "skipped", "failed", "refused"}`. Verified: no consumer breaks (CLI spreads the dict; autopipe does not consume it; cron is non-fatal); the only assertion to rewrite is `tests/test_display_coverage_parallel.py:54`.

### D4 (#1446) — the price of refusing: perpetual rescans, bounded and measured
A refused run keeps its old `refreshed_at` (it is in the skipped SET list, `:567`), so it stays stale and the cron's `--all --skip-fresh` rescans it with the full CTE every tick until its keys are backfilled (#1408 cutover, after which the refresh succeeds and the row heals) or an operator runs `--force`. Today's behaviour ("zero once, then never rescan") is replaced by "never zero, rescan each tick". Cost bound: one empty-scan CTE per stale legacy run per tick (indexed on the surrogate keys, returning zero rows fast). T6 measures on node-27 how many runs currently satisfy "stale AND key-NULL AND populated" so the standing cost is a number in the PR, and the runbook names the two remedies.

### D5 (#1725) — one scenario, two paths, N=3
Parametrize `workers in (1, 2)`; inject a `connect` callable that raises for exactly the second of three run ids; assert the four-key dict `{"refreshed": 2, "skipped": 0, "failed": 1, "refused": 0}`, survivors committed and closed, the failing path saw no commit, and the injected `connect` raising (the `:723` hoist point) is inside the `try`. Red-proof in the PR body: delete the `except Exception` arm → both parametrizations fail; restore → pass.

## Invariant Matrix

- Governing invariant: a coverage row can only go from populated to zero when the caller says `force`, on every refresh path; one run's failure or refusal never stops the batch or alters the other runs' outcomes, on either worker path.
- Source-of-truth identity/contract: `hydro.run_display_coverage.segment_count` per `run_id`; the `force` parameter of `_REFRESH_SQL`; summary dict keys; CLI exit 3 + `DISPLAY_COVERAGE_REFRESH_REFUSED` line.
- Producers: `_refresh`, `refresh_run_display_coverage`, `refresh_all_run_display_coverage`, `scripts/node27_refresh_coverage.py`.
- Validators/preflight: the conditional `WHERE`; `RefreshOutcome.refused = candidates − returned`; `DisplayCoverageRefreshRefused` (single-run only).
- Storage/cache/query: `_REFRESH_SQL` (changed: `force` param + conditional update).
- Public routes/entrypoints: the CLI (`--run-id`, `--all`, `--force`); autopipe tick calling `--run-id` and cron `--all --skip-fresh`.
- Frontend/downstream consumers: `/api/v1/layers` coverage freshness — refused runs are not written, so nothing downstream changes.
- Failure paths/rollback/stale state: refusal leaves no write and a rolled-back connection; `failed` and `refused` are distinct; refused runs stay stale and are rescanned (D4).
- Evidence/audit/readiness: node-27 real-DB run of the integration suite; D4 count query; red-proofs in the PR body.
- Regression rows:
  - legacy run (all-NULL keys) with existing `segment_count=12`, no force -> `DisplayCoverageRefreshRefused(run_id, 12, …)`, row unchanged; CLI exit 3 with the structured line.
  - same run with `force=True` / `--force` -> row updated to 0.
  - new run with no coverage row and empty scan -> row written with 0; existing row with 0 and empty scan -> rewritten with 0 (`refreshed_at` bumps).
  - all-runs form `_refresh(conn, None)` -> populated legacy rows skipped and left unchanged, others in `refreshed`, `refused == []` by contract; `tests/test_display_coverage_refresh.py:79,104,110` updated to the new parameter/return shape.
  - non-candidate run (no header row) that still owns an old populated coverage row -> `RefreshOutcome([], [])`, `refresh_run_display_coverage` returns `False`, batch counts `skipped`, autopipe sees `no_coverage_row` — never `refused`.
  - batch of 3 with one raising connect, workers 1 and 2 -> `{"refreshed": 2, "skipped": 0, "failed": 1, "refused": 0}`; batch with one legacy run -> `refused: 1`, others refreshed, their `refreshed_at` bumped.
  - Unchanged sibling: cron invocation and `scripts/node27_autopipe_cron.sh` untouched; #1719 `connect=` seam still honoured; autopipe `refresh_failed_rc` handling unchanged.

## Boundary surfaces

Write/overwrite surface: `_REFRESH_SQL` (now conditional). Public entrypoints: CLI + autopipe + cron. Stale-state: refused runs stay stale by design, priced in D4. Unchanged downstream: `/api/v1/layers`, MVT revision.
