# Run node-27 integration tests against a throwaway PostgreSQL instance

## Why

Real-database pytest on node-27 creates and drops one `nhms_it_<uuid>`
database per test on the **production postmaster** (#3376). PostgreSQL 15
has a race between `DROP DATABASE` and an autovacuum worker starting in that
database: the worker re-creates the statistics entry of the dropped database,
the launcher keeps the dropped database in its rotation for ever, and once it
reaches the tail of the rotation the launcher stops sending workers into any
existing database. Measured on 2026-11-25: 839 drops in 20 days, six races,
no autovacuum in `nhms` for nine days (#3234; it is the fourth occurrence,
after #1769, #1770 and #2696). Restarting the launcher only lasts until the next
race. The owner chose option A of #3376 on 2026-11-25: move the test
databases off the production postmaster.

## What changes

- **A tool, `scripts/node27_integration_pg.py`**, with four subcommands:
  `start`, `stop`, `status`, `run -- <command>`. `start` runs one container,
  `nhms-it-db`, from the image id of the production container (the same
  PostgreSQL and TimescaleDB binaries by construction), with its own data
  directory under `/home` and a loopback port that is not the production
  one. `run` executes a command with the integration opt-in and the
  instance's URL in the child's environment. `stop` removes the container
  and its directory.
- **A tripwire in `tests/conftest.py`**: a pytest session that has opted in
  to integration and whose integration URL names port 55432 (the documented
  production endpoint on node-27) ends with a usage error before any test
  runs.
- **Documentation and root instructions** say that node-27 integration runs
  go through the tool, and the runbook section on the stalled launcher gets
  the three amendments found after it merged (sweep bound, required role,
  mechanism confirmed by the restart).

## What does not change

- `tests/conftest.py` still only knows a server URL and still creates and
  drops `nhms_it_<uuid>` databases on the server it is pointed at; CI
  (`localhost:5432`) and local runs are untouched.
- No test is edited. No application code is edited.
- The production container, its data and its configuration are not touched.
  The tool reads one fact from it (`docker inspect nhms-db`, the image id).
- The production roles and `nhms_display_ro` privileges are unchanged (the
  identification query in the runbook keeps needing the superuser).

## Decisions

- **D1 A tool, not a paragraph in a runbook.** The recipe has six ways to go
  wrong that matter on a production host (wrong container name in `rm`,
  wrong directory in `rm -rf`, the production port, a password in `ps`
  output or in the tool's own output, data on the 26 GB root volume, an
  instance without memory limits next to the production postmaster). Each
  is a refusal in code with a test, instead of a sentence an operator or
  agent has to remember.
- **D2 Python, like the other `scripts/node27_*.py` tools.** Password
  generation, file modes, argument lists and refusals are testable with a
  fake `docker` on `PATH`; a shell script of the same size is not.
- **D3 Image by id from the production container.** A tag can move
  (`docker inspect nhms-db --format '{{.Image}}'` is the rule the rebuild
  runbook already states). When the production container does not exist the
  tool fails closed: it is a node-27 tool.
- **D4 The instance carries the production settings that change test
  behaviour, not the ones sized for production data.** Carried:
  `shared_preload_libraries=timescaledb`, `max_connections=100`,
  `max_locks_per_transaction=512`, `max_worker_processes=59`,
  `timescaledb.max_background_workers=16`, `timezone=Etc/UTC`. Not carried:
  buffer and work memory, parallelism, checkpoint and autovacuum tuning. The
  cluster's collation and encoding come from the image; `start` verifies
  them (`C.UTF-8`, `UTF8`, as measured on production) and fails if they
  differ, because sort-sensitive tests would silently diverge.
- **D5 Durability is off** (`fsync`, `synchronous_commit`,
  `full_page_writes`): every database in the instance is disposable, and the
  suite's cost on node-27 is mostly `CREATE DATABASE` plus migrations.
- **D6 Bounded footprint.** `--memory 8g --cpus 8 --shm-size 1g`, container
  log capped (`max-size=20m`, `max-file=2`, because container logs live on
  the root volume), telemetry off, no restart policy (after a host reboot
  the instance is simply absent and `start` begins from nothing).
- **D7 The password never appears in an argument list or on stdout.** It is
  generated by `start`, written to a `0600` env file inside the instance
  directory, passed to docker with `--env-file`, and handed to the child of
  `run` through the environment only.
- **D8 The tripwire is a port check, and says so.** It catches the
  documented way of reaching the production postmaster from node-27
  (`127.0.0.1:55432`), including through the generic `DATABASE_URL`
  compatibility path. It is not containment: an address that reaches the
  same server on another port is not seen. Nothing in this repository uses
  port 55432 for an integration URL (CI uses 5432, the development compose
  file does not publish 55432).
- **D9 `stop` refuses while a `run` is alive**, because the node-27 host is
  shared between sessions. `run` holds a shared lock on a file beside the
  instance directory for as long as its command (and that command's
  children) live; `start` and `stop` need the lock exclusively and refuse
  when they cannot have it; `stop --force` overrides. Connections are not a usable
  signal: the fixtures connect only to create and drop a database, so a
  session in the middle of its run usually has none.
- **D10 The tool removes only a container it created.** The container
  carries a label whose value is the resolved instance directory; removal
  inspects the label first and refuses a container named `nhms-it-db` that
  does not carry it.

## Known limits

- The password is not secret from everyone on the host: members of the
  docker group can read a container's environment with `docker inspect`,
  and pytest's long tracebacks can print fixture values, the integration
  URL among them. The instance is bound to loopback, holds only disposable
  databases and gets a new password at every `start`. What the tool
  guarantees is narrower: nothing it executes or prints carries the
  password. Receipts are searched for it before they are posted.
- The fake `docker` of the tests cannot show that readiness waits for the
  final server and not for the entrypoint's temporary one; the live run on
  node-27 is the oracle for that.
- The tripwire reads the port from the URL, and from `PGPORT` when the URL
  names none. A service file or another libpq default is not followed.
- A fresh `start` costs one `initdb` (measured in the evidence). The
  instance may be left running between runs.
- Other sources of `DROP DATABASE` on the production postmaster would hit the
  same PostgreSQL behaviour. None is known; the runbook keeps the
  identification and the remedy.
- Option D of #3376 (a governance code that names this mechanism) is not
  part of this change.
