## Why

Every write-path component on node-27 (autopipe ingest, download, timeseries compression, compression replay, timeseries retention) connects as the PostgreSQL superuser `nhms` (live `pg_roles` 2026-09-02: only `nhms` (super) and `nhms_display_ro` exist; all four hypertables are owned by `nhms`). A superuser can `COPY … FROM PROGRAM`, i.e. execute shell commands as the database OS user, on the host that also serves `https://test.nwm.ac.cn`. The exposure that made this an incident (port on `0.0.0.0`, unrotated passwords) was closed on 2026-08-23; what remains is the missing least-privilege layer on the write side. The env templates already name `nhms_ingest_rw` / `nhms_download_rw`, but no such roles exist and the tiering templates still say `REPLACE_ME_WRITER`.

The core unknown named by #1774 was measured in a disposable TimescaleDB 2.10.2 / PG 15.2 container (same versions as node-27): `compress_chunk`, `decompress_chunk`, `drop_chunks`, `chunks_detailed_size` and `ANALYZE <chunk>` all require the hypertable **owner** (a plain non-superuser role suffices; `ALTER TABLE … OWNER TO` cascades to existing chunks and the compressed hypertable; new chunks inherit the owner). A DML-only grantee can read `timescaledb_information.chunks`, INSERT into new and compressed ranges, DELETE in uncompressed chunks, and is refused `compress_chunk` ("must be owner of hypertable"), `ANALYZE` (skipped with a warning — which would silently kill the #1643 stats guard), `COPY … FROM PROGRAM`, `CREATE ROLE` and `CREATE TABLE`.

## What Changes

- Two login roles, matching the existing templates: `nhms_ingest_rw` — owner of every table/sequence/view in the application schemas (`core`, `hydro`, `met`, `ops`, `map`, `flood`; chunks follow their hypertables) because both stats-guard ANALYZE legs (#1643 chunks, #1468 authority tables) and the tiering functions require ownership; used by ingest, compression, cold-residency and retention. `nhms_download_rw` — DML-only on `met.*` (the download unit opens no DB connection today, measured; the role exists so the template's promise holds). Both `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`. `nhms` keeps the database, the extension and migrations, and leaves every recurring runtime env file except the two migration-class exceptions below. No `GRANT nhms TO <writer>`, no `REASSIGN OWNED BY nhms` (ownership is transferred by an explicit per-relation loop scoped to the six schemas).
- An idempotent provision script `db/roles/node27_write_roles.sql` (+ `scripts/node27_provision_write_roles.sh` runner using `docker exec nhms-db psql`) that creates/updates the roles, grants per the audited list, grants DML + sequence usage and sets `ALTER DEFAULT PRIVILEGES FOR ROLE nhms` for `nhms_ingest_rw` in the six schemas and for `nhms_download_rw` in `met` only (so migration-added tables stay usable before the re-run), transfers ownership with an explicit schema-scoped per-relation `ALTER … OWNER TO` sequence (one autocommitted statement per relation; tables before sequences, views/matviews included, absent schema tolerated, `lock_timeout`-bounded with retry; exhaustion leaves an audit-visible partial transfer that blocks cutover), grants `CREATE ON TABLESPACE nhms_cold` for the cold-residency `SET TABLESPACE` moves, and ends with an owner/flag/membership/tablespace/rule-trigger/stored-expression audit whose assertions raise on drift (psql non-zero → runner exit 3; a changed display SELECT set → exit 4), re-run after every migration and before every superuser-write session.
- A measured privilege inventory per component (tables × DML × TimescaleDB functions) written into `docs/runbooks/tier-node27-timeseries-storage.md` together with the ownership finding above; the `*.example` templates for compression/cold-residency/retention switch from `REPLACE_ME_WRITER` to `nhms_ingest_rw`; the retired archive-rebuild drill (no template exists since #1370; it needed `CREATEDB` and stays `nhms` in the runbook inventory and the guard allow-list) and `node27-timeseries-compression-replay.example` (its supervisor runs `pg_dump`, `migration_apply` via `psql --file`, `pg_restore` — migration-class work) keep `nhms` as documented exceptions.
- A repo-side guard test that the runtime `*.example` templates carry no `nhms` credential in any form (`nhms:` DSN user or `PGUSER=nhms`) outside the two allow-listed exceptions, and that the provision SQL names exactly the roles the templates use.
- node-27, staged: pre-merge only the additive `--roles-only` provision (roles, grants, default privileges, `pg_roles` flags, negative `COPY … FROM PROGRAM` probes); post-merge the ownership transfer inside a timer-stopped window (one autocommitted statement per relation, `lock_timeout` + retry, `relacl` diff, audit), each component run once under its new role from a detached worktree with both stats-guard legs reporting `ok`, then env cutover download → ingest → compression + cold-residency → retention with unit restarts and receipts. The ownership transfer is a scope expansion over the pre-authorized role creation and is stated as such in the PR body.
