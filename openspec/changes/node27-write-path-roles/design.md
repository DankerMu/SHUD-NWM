## Context

Issue #1774 — least-privilege write roles on the node-27 production database. Auth/permissions + production config + live DDL on the primary: fixture level `expanded`, repair intensity `high`. Measured facts (2026-09-02, disposable `timescale/timescaledb:2.10.2-pg15` matching node-27's PG 15.2 / TSDB 2.10.2): owner-role requirement for compress/decompress/drop_chunks/ANALYZE; ownership cascades to chunks; DML grantee behaviour as listed in the proposal; `ALTER DEFAULT PRIVILEGES FOR ROLE nhms` covers tables created later by `nhms`. Repo facts (fixture review, revision 1): the stats guard has **two** ANALYZE legs — chunks (`scripts/node27_autopipeline.py:1482`) and the authority-table repair leg `_STATS_GUARD_AUTHORITY_CANDIDATES_SQL` (`:1419-1435`, ordinary tables across `core`/`met`/`hydro`, run every tick at `:1663`), and a skipped non-owner ANALYZE is graded `status="warning"` (`:1490`), i.e. tick green, leg dead; the download unit's chain (`node27_download_once.sh` → `node27_download_cycles.py` → `nhms-gfs`/`nhms-ifs download`, `:648-657`) opens **no** database connection (no `execute(` in the script, no `psycopg2`/`DATABASE_URL` under `workers/data_adapters/`) — the `met.*` forcing DML is applied from the ingest lane (`scripts/node27_autopipeline.py:63-68,117`; `workers/forcing_producer/store.py:825-829`); the cold-residency lane runs inside `nhms-node27-timeseries-compression.service` (`infra/systemd/nhms-node27-timeseries-compression.service:8,10`, env `infra/env/node27-cold-residency.example:25` = a sixth writer DSN) and issues `ALTER TABLE/INDEX … SET TABLESPACE` on compressed chunks (`packages/common/compressed_chunk_cold_residency.py:421,422`) — chunk ownership plus `CREATE` on tablespace `nhms_cold` (the `CREATE TABLESPACE` itself lives in the one-time install/probe paths `node27_cold_tablespace_engine.py:201`, `compressed_chunk_cold_probe/shell.py:319`, not in the recurring unit); the compression-replay unit's entrypoint is `scripts/node27_timeseries_compression_supervisor.py` (`infra/systemd/nhms-node27-timeseries-compression-replay.service:12-13`), authenticating via `PGUSER`/`PGPASSWORD` (`infra/env/node27-timeseries-compression-replay.example:21-29`, forwarded at `supervisor.py:171-179`, `psql --dbname nhms` at `:1328-1338`) and whose run plan includes `pg_dump`, two `migration_apply` steps (`psql --file <migration>`) and `docker exec nhms-db pg_restore` (`:101-128,143,331-380`); `ALTER TABLE … OWNER TO` on a hypertable takes `AccessExclusiveLock` down the chunk tree while a compression tick may hold one chunk for up to 3600 s (`infra/env/node27-timeseries-compression.example:66`).

## Goals / Non-Goals

**Goals**: no recurring runtime unit on node-27 authenticates as a superuser except the two documented migration-class exceptions; every write component runs under a role that cannot execute programs or create roles/databases; provisioning is idempotent and re-runnable after migrations; cutover is receipted per unit and reversible; the #1643/#1468 stats-guard legs keep working.

**Non-Goals**: `pg_hba.conf` `trust` lines; `ssl=off`; `packages/common/migrate.py` (migrations stay on `nhms`); #1770/#1769 vacuum/statistics; a per-lane tiering role (D2); password rotation (done 08-23); the one-time cold-tablespace install (`CREATE TABLESPACE`, superuser by nature, documented).

## Decisions

### D1 — two login roles, as the templates already say
`nhms_ingest_rw` and `nhms_download_rw` (`scripts/local_pg.sh:151` CREATE ROLE shape). Rejected: a single `nhms_rw` and a third `nhms_tiering_rw` (D2).

### D2 — `nhms_ingest_rw` owns the application schema's objects; `nhms` keeps the database and runs migrations
Both stats-guard legs need ownership (chunks for the compression-capable hypertables, ordinary tables in `core`/`met`/`hydro` for the repair leg), and PG 15 has no `MAINTAIN`. Ownership is therefore transferred for **every table, sequence and view in the application schemas** (`core`, `hydro`, `met`, `ops`, `map`, `flood`) by an explicit, idempotent per-relation `ALTER … OWNER TO nhms_ingest_rw` sequence generated from `pg_class` filtered to those schemas and executed by the runner **one statement per transaction** (psql autocommit, not a single `DO` block), so each completed transfer releases its `AccessExclusiveLock` immediately — never `REASSIGN OWNED BY nhms` (moves the database, schemas, extension-adjacent objects) and never `GRANT nhms TO …`. The `_timescaledb_*` schemas are excluded (chunks follow their hypertable). Consequence: ingest, compression, retention and cold-residency all run as `nhms_ingest_rw` (replay excluded, D5). Ownership covers existing relations; **DML grants are kept as well** — `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES` + `USAGE ON ALL SEQUENCES` in the six schemas to `nhms_ingest_rw`, plus `ALTER DEFAULT PRIVILEGES FOR ROLE nhms IN SCHEMA core, hydro, met, ops, map, flood GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES, USAGE ON SEQUENCES TO nhms_ingest_rw` — so a table added by a later migration (owned by `nhms` until the provision re-run) is still readable/writable by ingest during the drift window and only its ANALYZE entry degrades to `warning`. `nhms_download_rw` gets the same shape restricted to `met.*` (grants + default privileges + schema/sequence `USAGE`). The ownership loop processes relkind `r`/`p` before `S` (an owned sequence follows its table; a standalone `ALTER SEQUENCE … OWNER TO` on an `OWNED BY` sequence errors), includes `v` and `m` so a future view/matview cannot make the audit fail with no loop branch to fix it, and tolerates an absent schema (`flood` is provisioned outside `db/` and does not exist in the disposable container). Residual, accepted: the ingest credential's blast radius becomes "drop or truncate any application relation" — no direct `COPY … FROM PROGRAM`, no role/database creation, no direct catalog escape — traded for the #1643/#1468 legs staying alive. Ownership also carries `CREATE RULE` / `CREATE TRIGGER`, and a rule action or trigger body executes as whichever role next writes the relation — including superuser `nhms` during migrations, seeds and the replay supervisor — which is an indirect path to `pg_read_file`, `lo_export` into PGDATA and `COPY … TO PROGRAM` (round-2 review, reproduced in a container). Two mitigations ship with the provision SQL: (1) prevention — a superuser-owned `ddl_command_start` event trigger (schema `nhms_guard`, installed in the additive phase so `--roles-only` already carries it) that raises on the rule/trigger DDL family when `session_user` is either write role (they hold no membership, so `SET ROLE` cannot evade it, and they cannot drop a superuser-owned event trigger; the guard keys on `session_user`, so a grant of a write role *to* another role would let that role `SET ROLE` past it — the second reason the membership audit refuses the grantee direction in every mode). Measured gap: TimescaleDB's process-utility hook handles `CREATE TRIGGER` on a hypertable (and on `_compressed_hypertable_*`) itself and never reaches `ddl_command_start`, so on `hydro.river_timeseries` and `met.forcing_station_timeseries` the event trigger does not fire and a planted trigger lands and propagates to every chunk (container transcript §15; ordinary tables and chunks are refused as designed, `CREATE RULE` on a hypertable is refused by TimescaleDB itself). The superuser write that evaluates such a trigger is the replay `pg_restore` `COPY` into compressed chunks — `compress_chunk` / retention do not fire row triggers — which is why §9.6 requires the audit-only run before every superuser-write session. (2) detection — the strict audit enumerates `pg_rewrite` (six schemas plus every `_timescaledb_internal` relation owned by either write role — owner-scoped, so TimescaleDB's own catalog relations are never scanned; `rulename <> '_RETURN'`) and `pg_trigger` (`NOT tgisinternal AND tgname <> 'ts_insert_blocker'`) against the explicit allowlist of the four `met` triggers created by `db/migrations/000043_canonical_grid_snapshot.sql`, and fails on anything else. The event trigger covers the rule/trigger DDL family (`CREATE`/`ALTER`/`DROP RULE`, `CREATE`/`ALTER`/`DROP TRIGGER`); it deliberately does not cover `ALTER TABLE`, which the cold-residency lane needs for `SET TABLESPACE`. The same gadget therefore survives in `ALTER TABLE` form — a column `DEFAULT` or `CHECK` expression that calls a superuser-only function (`pg_read_file`, `lo_export`, …) is evaluated by whichever role next writes the row, and `ALTER TABLE … DISABLE TRIGGER` can switch an allow-listed trigger off (reproduced in the transcript §12). Those are closed by detection rather than prevention: the strict audit scans every stored expression tree in the six schemas and in the write-role-owned `_timescaledb_internal` relations — column defaults (`pg_attrdef.adbin`), `CHECK` constraints (`pg_constraint.conbin`), rule actions (`pg_rewrite.ev_action`, `_RETURN` excluded) — for `:funcid`/`:opfuncid` nodes plus every trigger function (`pg_trigger.tgfoid`), resolves them in `pg_proc`, and fails when a referenced function is **untrusted for a superuser writer** — the invariant is provenance, not executability: anything the write role can author or attach to a relation it owns is evaluated with the authority of whoever writes the row, so the sweep flags a function when its schema is a temp schema (`pg_temp_%` / `pg_toast_temp_%` — the only place the write role can author a function body), or its owner is not `rolsuper`, or the write role cannot `EXECUTE` it, or it is on an explicit deny-list of PUBLIC-executable `pg_catalog` functions with superuser-sensitive effects (`set_config` — which a superuser-evaluated default used to flip `session_replication_role` and switch every non-replica trigger off for the session — `pg_terminate_backend`, `pg_cancel_backend`, `pg_reload_conf`, `pg_notify`, `pg_sleep*`, the advisory-lock family). Round 3 measured why the executability proxy was wrong: a `pg_temp`-owned function and `set_config` both pass `has_function_privilege` and both reached OS command execution / integrity-guard bypass under a superuser `INSERT` with the audit reporting clean. The deny-list is a recorded residual (incomplete by construction); the temp-schema and owner legs are structural. TimescaleDB's `ts_insert_blocker` is excluded by function identity (`tgfoid IS DISTINCT FROM to_regprocedure('_timescaledb_internal.insert_blocker()')`), never by name — `CREATE OR REPLACE TRIGGER ts_insert_blocker … EXECUTE FUNCTION <other>` on a hypertable is a planted trigger (measured: RCE with a temp-schema body, ingest DoS with a borrowed `met` trigger function) — and the four allow-listed triggers must be present (`count(*) = 4`) as well as enabled. `pg_depend` is deliberately not the mechanism: PostgreSQL records no dependency rows on pinned built-ins such as `pg_read_file`, so a `pg_depend` walk sees zero rows for exactly the gadget it must catch (measured in the container transcript §14). The scan materialises its result set in a session temp table (`pg_temp.nhms_audit_function_refs`, dropped at the end) so the per-mode listing, the strict verdict and the T7 receipt read one scan (a function the owner may not call directly but can smuggle into an expression evaluated as superuser is exactly the escalation), and it fails when an allow-listed trigger is not enabled (`tgenabled <> 'O'`). `REVOKE TEMPORARY` is adopted as prevention in the full (post-merge) mode, not in `--roles-only`: `TEMP` reaches the write roles through PUBLIC (`datacl {=Tc/nhms,…}`), so the effective statement is `REVOKE TEMPORARY ON DATABASE … FROM PUBLIC` followed by `GRANT TEMPORARY … TO nhms_display_ro` (display keeps exactly today's privilege; the superuser is unaffected) — the one non-additive statement in the change, which is why it lives in the ownership/tightening phase. It removes the write roles' only function-authoring surface (measured: `has_schema_privilege(…, 'CREATE')` is false for every schema); the `COPY … FROM PROGRAM` probe creates its scratch table as the superuser before `SET LOCAL ROLE` so it keeps asserting SQLSTATE 42501 from `COPY` itself. It does not replace detection: a persistent rule/trigger or a `pg_catalog` gadget needs no temp object, and the audit stays the gate before every superuser write. The audit also asserts the tightening itself — `has_database_privilege(<write role>, current_database(), 'TEMP')` must be false — and that verdict is gated on `strict_audit` rather than on `do_ownership` because the §9.6 audit-only invocation (`do_ownership=off`, `strict_audit=on`) is the only place a TEMP grant re-issued after cutover would be seen; consequence recorded in §9.6: a strict audit-only run against a database that has never had the full provision (or that lacks migration `000043`, whose four triggers the presence leg counts) exits 3 by design, and `--roles-only` (non-strict) stays quiet. Removing the superuser-write half of the gadget (migrations and replay off `nhms`) is a documented non-goal here and stays a follow-up. Cold residency additionally needs `GRANT CREATE ON TABLESPACE nhms_cold TO nhms_ingest_rw` (tablespace exists on node-27; the grant is conditional on its presence). Rejected: separate owner-group role (pure indirection once ingest must own everything anyway); leaving the authority leg dead (silent loss of the #1468 repair).

### D3 — the inventory is measured, then encoded
The implementer derives the per-component requirement by (a) static scan reachable from each unit's entrypoint widened beyond DML to `ANALYZE`, `ALTER … SET TABLESPACE`, `CREATE/ALTER/DROP`, `psql --file`, `pg_dump`/`pg_restore` call sites, and (b) running each component's real-DB test suite / dry-run locally against a disposable TimescaleDB container as the candidate role, converting every `permission denied` / skipped-ANALYZE warning into a grant or a documented exception. The download lane's measured requirement is "no DB connection today"; `nhms_download_rw` is still provisioned to the template's promise (DML on `met.*`) so the env file matches the template and a future adapter write does not land on `nhms`. The final inventory table is a runbook artifact; the SQL is its executable form; the guard test asserts the SQL covers at least the statically scanned targets.

### D4 — idempotent SQL with a trailing audit
Roles via `DO $$ … IF NOT EXISTS (SELECT 1 FROM pg_roles …) $$`; passwords never in the repo — the runner forwards `NODE27_INGEST_RW_PASSWORD` / `NODE27_DOWNLOAD_RW_PASSWORD` by name (`docker exec -e`) and the SQL issues `ALTER ROLE … PASSWORD` via `\getenv` under suppressed statement logging, skipping when the variable is unset (an exported-but-empty variable is refused by the runner's `${!var:+x}` presence check; a direct psql invocation with an empty variable would set an empty password — documented in the SQL header). The script installs the rule/trigger-blocking event trigger in the additive phase (idempotent: drop-and-recreate, superuser-owned) and ends with a query over `pg_roles` (flags) and `pg_auth_members` (both directions — a write role as member, and a write role granted to any other role such as `nhms_display_ro`) (any membership of either write role is a security regression — `GRANT nhms TO …` would otherwise pass the flags check while granting superuser via `SET ROLE`), over `has_tablespace_privilege('nhms_ingest_rw','nhms_cold','CREATE')` when the tablespace exists (explicit skip line when absent), over owners of every relation in the application schemas + the two hypertables, and over `nhms_display_ro`'s effective `SELECT` set (`has_table_privilege` per relation) — `ALTER … OWNER TO` rewrites ACL grantor references, so the display role's grants are asserted explicitly rather than assumed; the runner fails when any audit predicate raises (psql non-zero → runner exit 3) and when `nhms_display_ro`'s effective SELECT set differs across the transfer (exit 4); there is no committed expected-output literal. The display role's grants live only in the live catalog (no `db/` source), so the pre-merge receipt also captures `relacl` before and after the loop. Re-run after every migration is written into the migration runbook step.

### D5 — staged cutover: additive pre-merge, ownership + component runs post-merge
Pre-merge (receipt session, first in queue, from a detached worktree, no unit env touched, **no lock footprint**): run the provision script in `--roles-only` mode — roles + flags, DML grants, sequence usage, default privileges, tablespace grant, the `nhms_guard` schema with its superuser-owned event-trigger function and the `nhms_guard_no_write_role_rules_triggers` event trigger (the only non-role objects the additive phase creates), `pg_roles` flags, the membership / tablespace / rule-trigger / function-privilege audits, and the two negative `COPY … FROM PROGRAM` probes (both roles). Everything in that mode is additive: no `ALTER … OWNER TO` executes, no relation lock is taken, and the units keep running as `nhms`. The proof that `compress_chunk` / `drop_chunks` / both ANALYZE legs / `SET TABLESPACE` work under `nhms_ingest_rw` comes from the local disposable container (T2 transcript in the PR), the same staging shape as #1714 D5. Rationale: at pre-merge time the provision SQL is unreviewed, and an ownership transfer over every application relation on the public-facing primary is a larger action than the role creation the user pre-authorized — the PR body states that scope expansion in one sentence, and the transfer waits for the reviewed merge.
Post-merge (same ssh session, after `git pull --ff-only` on the deployed checkout): stop `nhms-node27-timeseries-compression.timer`, `nhms-node27-timeseries-retention.timer` (its `drop_chunks` takes `AccessExclusiveLock` on the same chunk tree) and the autopipe timer, confirm no in-flight `compress_chunk`/`drop_chunks`/tick (`pg_stat_activity`); the display API (`nhms_display_ro`, public site) cannot be stopped and holds `AccessShareLock` on served relations, so the runner executes the ownership loop **one autocommitted statement per relation** (generated from `pg_class`, relkind r/p before S, plus v/m; never a single `DO` transaction) under `SET lock_timeout = '5s'` with up to 5 retry passes (skip-and-retry, never an unbounded wait behind a display scan): the display-visible stall is bounded by one relation's `lock_timeout`, not by the loop's duration. The passes run back-to-back with no inter-pass delay (≈5 s × passes of wall clock against a holder that never releases), so a holder outliving the loop is reported as partial transfer (exit 3) rather than waited out; the operator re-runs after the holder clears, or passes `--pass-interval` to space the passes. Retry exhaustion leaves a **partial, audit-visible transfer** (the trailing audit lists relations still owned by `nhms`, the runner exits non-zero, and the env cutover does not proceed) — never a rollback. A partial transfer is safe because every unit still connects as `nhms`, a superuser, for which `object_ownercheck` short-circuits, so `compress_chunk`/`drop_chunks`/`ANALYZE` keep passing on relations `nhms` no longer owns. `relacl` is captured before/after inside the runner (the display role's grants have no repo source of truth, so the audit is a before/after capture, not a committed literal) and diffed. Then: per-component run under the new roles from a detached worktree with scratch env files (autopipe dry tick with both stats-guard legs `ok`, compression `--enforce` on one eligible chunk or dry-run if none, retention dry-run, cold-residency dry-run, download dry-run as the no-DB control) → env cutover download → ingest → compression + cold-residency → retention, restart each unit, receipt each (`journalctl` + `pg_stat_activity.usename`), restart timers. Exceptions (documented, not TODOs): `node27-archive-rebuild-drill.env` (needs `CREATEDB`, `postgres` db) and `node27-timeseries-compression-replay.env` (supervisor runs `pg_dump`, `migration_apply`, `pg_restore` — migration-class DDL) keep `nhms` (`PGUSER`) and are listed as such in the template guard's allow-list and in the spec scenario. Rollback = restore the env file's previous URL (kept as `*.env.pre-1774`) and restart; ownership stays with `nhms_ingest_rw` (superuser `nhms` is unaffected by it).

## Invariant Matrix

- Governing invariant: no recurring node-27 runtime unit authenticates as a superuser except the two documented migration-class lanes, `nhms_ingest_rw` owns every application-schema relation so both stats-guard legs and all tiering functions work, and the whole state is reproducible from one idempotent script whose audit fails on drift.
- Source-of-truth identity/contract: `db/roles/node27_write_roles.sql`; `pg_roles` flags; relation `relowner` in the application schemas; env `DATABASE_URL` user / `PGUSER`.
- Producers: the provision SQL/runner; env files (operator).
- Validators/preflight: trailing audit query; `tests/test_node27_write_roles.py` (templates carry no `nhms` credential in any form — `nhms:` DSN or `PGUSER=nhms` — except the two allow-listed lanes; SQL names exactly the template roles; SQL ownership loop covers the six schemas; ingest default-privilege block and display-audit clause present; SQL grants ⊇ scanned `met.*` targets for download; forbidden statements absent: `REASSIGN OWNED`, `GRANT nhms TO`, single-transaction `DO` around the ownership loop).
- Storage/cache/query: ownership/grants in the catalog; `ALTER DEFAULT PRIVILEGES`; tablespace `CREATE` grant.
- Public routes/entrypoints: six env files (ingest, download, compression, cold-residency, retention, replay-exception); `scripts/node27_provision_write_roles.sh`.
- Frontend/downstream consumers: none (display stays on `nhms_display_ro`).
- Failure paths/rollback/stale state: a missing privilege surfaces as `permission denied` in the unit's journal (+ `OnFailure` where present) or as a `warning` stats-guard entry; rollback by env restore; new migration tables are owned by `nhms` until re-provision (audit-visible) but remain writable via default privileges; a lock-timeout during the ownership loop is retried per relation (autocommit), so the display API never waits longer than one relation's `lock_timeout`; exhaustion = partial transfer reported by the audit, cutover blocked.
- Evidence/audit/readiness: pre-merge role/probe receipts incl. both stats-guard legs `ok` in the dry tick; post-merge per-unit receipts; `pg_roles` output; redacted `grep` of env files.
- Regression rows:
  - provision script run twice -> identical audit output, no error; run after a migration that adds `hydro.newtab` -> ingest INSERT into `hydro.newtab` succeeds during the window (default privileges), only its ANALYZE entry is `warning`, audit reports the owner drift, re-run fixes it.
  - `nhms_ingest_rw`: `compress_chunk`/`drop_chunks`/chunk `ANALYZE`/authority-table `ANALYZE`/`SET TABLESPACE nhms_cold` succeed; `COPY … FROM PROGRAM` -> `must be superuser`; `CREATE ROLE`/`CREATE DATABASE` -> denied.
  - `nhms_download_rw`: INSERT into a `met.*` table succeeds (privilege-shape probe, not a lane path); `compress_chunk` -> `must be owner`; `COPY … FROM PROGRAM` denied.
  - unchanged sibling: `nhms_display_ro` `SELECT` set identical before/after (audit query + `relacl` capture); drill and replay envs keep `nhms`; migrations still run as `nhms`; display API unaffected.

## Boundary surfaces

Auth surface: role creation/grants/ownership (DDL on production, pre-approved by the user) inside a timer-stopped window. Config: six env files + templates. Publish/rollback: env cutover per unit with `*.env.pre-1774` backups. Unchanged downstream: display role, migration role, schemas, replay and drill lanes.
