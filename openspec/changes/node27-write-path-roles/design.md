## Context

Issue #1774 — least-privilege write roles on the node-27 production database. Auth/permissions + production config + live DDL on the primary: fixture level `expanded`, repair intensity `high`. Measured facts (2026-09-02, disposable `timescale/timescaledb:2.10.2-pg15` matching node-27's PG 15.2 / TSDB 2.10.2): owner-role requirement for compress/decompress/drop_chunks/ANALYZE; ownership cascades to chunks; DML grantee behaviour as listed in the proposal; `ALTER DEFAULT PRIVILEGES FOR ROLE nhms` covers tables created later by `nhms`. Repo facts (fixture review, revision 1): the stats guard has **two** ANALYZE legs — chunks (`scripts/node27_autopipeline.py:1482`) and the authority-table repair leg `_STATS_GUARD_AUTHORITY_CANDIDATES_SQL` (`:1419-1435`, ordinary tables across `core`/`met`/`hydro`, run every tick at `:1663`), and a skipped non-owner ANALYZE is graded `status="warning"` (`:1490`), i.e. tick green, leg dead; the download unit's chain (`node27_download_once.sh` → `node27_download_cycles.py` → `nhms-gfs`/`nhms-ifs download`, `:648-657`) opens **no** database connection (no `execute(` in the script, no `psycopg2`/`DATABASE_URL` under `workers/data_adapters/`) — the `met.*` forcing DML is applied from the ingest lane (`scripts/node27_autopipeline.py:63-68,117`; `workers/forcing_producer/store.py:825-829`); the cold-residency lane runs inside `nhms-node27-timeseries-compression.service` (`infra/systemd/nhms-node27-timeseries-compression.service:8,10`, env `infra/env/node27-cold-residency.example:25` = a sixth writer DSN) and issues `ALTER TABLE/INDEX … SET TABLESPACE` on compressed chunks (`packages/common/compressed_chunk_cold_residency.py:414,422`) — chunk ownership plus `CREATE` on tablespace `nhms_cold` (the `CREATE TABLESPACE` itself lives in the one-time install/probe paths `node27_cold_tablespace_engine.py:201`, `compressed_chunk_cold_probe/shell.py:319`, not in the recurring unit); the compression-replay unit's entrypoint is `scripts/node27_timeseries_compression_supervisor.py` (`infra/systemd/nhms-node27-timeseries-compression-replay.service:12-13`), authenticating via `PGUSER`/`PGPASSWORD` (`infra/env/node27-timeseries-compression-replay.example:3-8`, forwarded at `supervisor.py:171-179`, `psql --dbname nhms` at `:1328-1338`) and whose run plan includes `pg_dump`, two `migration_apply` steps (`psql --file <migration>`) and `docker exec nhms-db pg_restore` (`:101-128,143,331-380`); `ALTER TABLE … OWNER TO` on a hypertable takes `AccessExclusiveLock` down the chunk tree while a compression tick may hold one chunk for up to 3600 s (`infra/env/node27-timeseries-compression.example:61`).

## Goals / Non-Goals

**Goals**: no recurring runtime unit on node-27 authenticates as a superuser except the two documented migration-class exceptions; every write component runs under a role that cannot execute programs or create roles/databases; provisioning is idempotent and re-runnable after migrations; cutover is receipted per unit and reversible; the #1643/#1468 stats-guard legs keep working.

**Non-Goals**: `pg_hba.conf` `trust` lines; `ssl=off`; `packages/common/migrate.py` (migrations stay on `nhms`); #1770/#1769 vacuum/statistics; a per-lane tiering role (D2); password rotation (done 08-23); the one-time cold-tablespace install (`CREATE TABLESPACE`, superuser by nature, documented).

## Decisions

### D1 — two login roles, as the templates already say
`nhms_ingest_rw` and `nhms_download_rw` (`scripts/local_pg.sh:151` CREATE ROLE shape). Rejected: a single `nhms_rw` and a third `nhms_tiering_rw` (D2).

### D2 — `nhms_ingest_rw` owns the application schema's objects; `nhms` keeps the database and runs migrations
Both stats-guard legs need ownership (chunks for the compression-capable hypertables, ordinary tables in `core`/`met`/`hydro` for the repair leg), and PG 15 has no `MAINTAIN`. Ownership is therefore transferred for **every table, sequence and view in the application schemas** (`core`, `hydro`, `met`, `ops`, `map`, `flood`) by an explicit, idempotent per-relation `ALTER … OWNER TO nhms_ingest_rw` sequence generated from `pg_class` filtered to those schemas and executed by the runner **one statement per transaction** (psql autocommit, not a single `DO` block), so each completed transfer releases its `AccessExclusiveLock` immediately — never `REASSIGN OWNED BY nhms` (moves the database, schemas, extension-adjacent objects) and never `GRANT nhms TO …`. The `_timescaledb_*` schemas are excluded (chunks follow their hypertable). Consequence: ingest, compression, retention and cold-residency all run as `nhms_ingest_rw` (replay excluded, D5). Ownership covers existing relations; **DML grants are kept as well** — `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES` + `USAGE ON ALL SEQUENCES` in the six schemas to `nhms_ingest_rw`, plus `ALTER DEFAULT PRIVILEGES FOR ROLE nhms IN SCHEMA core, hydro, met, ops, map, flood GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES, USAGE ON SEQUENCES TO nhms_ingest_rw` — so a table added by a later migration (owned by `nhms` until the provision re-run) is still readable/writable by ingest during the drift window and only its ANALYZE entry degrades to `warning`. `nhms_download_rw` gets the same shape restricted to `met.*` (grants + default privileges + schema/sequence `USAGE`). The ownership loop processes relkind `r`/`p` before `S` (an owned sequence follows its table; a standalone `ALTER SEQUENCE … OWNER TO` on an `OWNED BY` sequence errors), includes `v` and `m` so a future view/matview cannot make the audit fail with no loop branch to fix it, and tolerates an absent schema (`flood` is provisioned outside `db/` and does not exist in the disposable container). Residual, accepted: the ingest credential's blast radius becomes "drop or truncate any application relation" — still strictly smaller than superuser (no `COPY … FROM PROGRAM`, no role/database creation, no catalog escape), and traded for the #1643/#1468 legs staying alive. Cold residency additionally needs `GRANT CREATE ON TABLESPACE nhms_cold TO nhms_ingest_rw` (tablespace exists on node-27; the grant is conditional on its presence). Rejected: separate owner-group role (pure indirection once ingest must own everything anyway); leaving the authority leg dead (silent loss of the #1468 repair).

### D3 — the inventory is measured, then encoded
The implementer derives the per-component requirement by (a) static scan reachable from each unit's entrypoint widened beyond DML to `ANALYZE`, `ALTER … SET TABLESPACE`, `CREATE/ALTER/DROP`, `psql --file`, `pg_dump`/`pg_restore` call sites, and (b) running each component's real-DB test suite / dry-run locally against a disposable TimescaleDB container as the candidate role, converting every `permission denied` / skipped-ANALYZE warning into a grant or a documented exception. The download lane's measured requirement is "no DB connection today"; `nhms_download_rw` is still provisioned to the template's promise (DML on `met.*`) so the env file matches the template and a future adapter write does not land on `nhms`. The final inventory table is a runbook artifact; the SQL is its executable form; the guard test asserts the SQL covers at least the statically scanned targets.

### D4 — idempotent SQL with a trailing audit
Roles via `DO $$ … IF NOT EXISTS (SELECT 1 FROM pg_roles …) $$`; passwords never in the repo — the runner reads `NODE27_INGEST_RW_PASSWORD` / `NODE27_DOWNLOAD_RW_PASSWORD` from the environment and issues `ALTER ROLE … PASSWORD` separately, or skips when unset. The script ends with a query over `pg_roles` (flags) and `pg_auth_members` (any membership of either write role is a security regression — `GRANT nhms TO …` would otherwise pass the flags check while granting superuser via `SET ROLE`), over `has_tablespace_privilege('nhms_ingest_rw','nhms_cold','CREATE')` when the tablespace exists (explicit skip line when absent), over owners of every relation in the application schemas + the two hypertables, and over `nhms_display_ro`'s effective `SELECT` set (`has_table_privilege` per relation) — `ALTER … OWNER TO` rewrites ACL grantor references, so the display role's grants are asserted explicitly rather than assumed; the runner fails if the output differs from the committed expectation. The display role's grants live only in the live catalog (no `db/` source), so the pre-merge receipt also captures `relacl` before and after the loop. Re-run after every migration is written into the migration runbook step.

### D5 — staged cutover: additive pre-merge, ownership + component runs post-merge
Pre-merge (receipt session, first in queue, from a detached worktree, no unit env touched, **no lock footprint**): run the provision script in `--roles-only` mode — roles + flags, DML grants, sequence usage, default privileges, tablespace grant, `pg_roles` flags, and the two negative `COPY … FROM PROGRAM` probes (both roles). Everything in that mode is additive: no `ALTER … OWNER TO` executes, no relation lock is taken, and the units keep running as `nhms`. The proof that `compress_chunk` / `drop_chunks` / both ANALYZE legs / `SET TABLESPACE` work under `nhms_ingest_rw` comes from the local disposable container (T2 transcript in the PR), the same staging shape as #1714 D5. Rationale: at pre-merge time the provision SQL is unreviewed, and an ownership transfer over every application relation on the public-facing primary is a larger action than the role creation the user pre-authorized — the PR body states that scope expansion in one sentence, and the transfer waits for the reviewed merge.
Post-merge (same ssh session, after `git pull --ff-only` on the deployed checkout): stop `nhms-node27-timeseries-compression.timer`, `nhms-node27-timeseries-retention.timer` (its `drop_chunks` takes `AccessExclusiveLock` on the same chunk tree) and the autopipe timer, confirm no in-flight `compress_chunk`/`drop_chunks`/tick (`pg_stat_activity`); the display API (`nhms_display_ro`, public site) cannot be stopped and holds `AccessShareLock` on served relations, so the runner executes the ownership loop **one autocommitted statement per relation** (generated from `pg_class`, relkind r/p before S, plus v/m; never a single `DO` transaction) under `SET lock_timeout = '5s'` with up to 5 retry passes (skip-and-retry, never an unbounded wait behind a display scan): the display-visible stall is bounded by one relation's `lock_timeout`, not by the loop's duration. The passes run back-to-back with no inter-pass delay (≈5 s × passes of wall clock against a holder that never releases), so a holder outliving the loop is reported as partial transfer (exit 3) rather than waited out; the operator re-runs after the holder clears, or passes `--pass-interval` to space the passes. Retry exhaustion leaves a **partial, audit-visible transfer** (the trailing audit lists relations still owned by `nhms`, the runner exits non-zero, and the env cutover does not proceed) — never a rollback. A partial transfer is safe because every unit still connects as `nhms`, a superuser, for which `object_ownercheck` short-circuits, so `compress_chunk`/`drop_chunks`/`ANALYZE` keep passing on relations `nhms` no longer owns. `relacl` is captured before/after inside the runner (the display role's grants have no repo source of truth, so the audit is a before/after capture, not a committed literal) and diffed. Then: per-component run under the new roles from a detached worktree with scratch env files (autopipe dry tick with both stats-guard legs `ok`, compression `--enforce` on one eligible chunk or dry-run if none, retention dry-run, cold-residency dry-run, download dry-run as the no-DB control) → env cutover download → ingest → compression + cold-residency → retention, restart each unit, receipt each (`journalctl` + `pg_stat_activity.usename`), restart timers. Exceptions (documented, not TODOs): `node27-archive-rebuild-drill.env` (needs `CREATEDB`, `postgres` db) and `node27-timeseries-compression-replay.env` (supervisor runs `pg_dump`, `migration_apply`, `pg_restore` — migration-class DDL) keep `nhms` (`PGUSER`) and are listed as such in the template guard's allow-list and in the spec scenario. Rollback = restore the env file's previous URL (kept as `*.env.pre-1774`) and restart; ownership stays with `nhms_ingest_rw` (superuser `nhms` is unaffected by it).

## Invariant Matrix

- Governing invariant: no recurring node-27 runtime unit authenticates as a superuser except the two documented migration-class lanes, `nhms_ingest_rw` owns every application-schema relation so both stats-guard legs and all tiering functions work, and the whole state is reproducible from one idempotent script whose audit fails on drift.
- Source-of-truth identity/contract: `db/roles/node27_write_roles.sql`; `pg_roles` flags; relation `relowner` in the application schemas; env `DATABASE_URL` user / `PGUSER`.
- Producers: the provision SQL/runner; env files (operator).
- Validators/preflight: trailing audit query; `tests/test_node27_write_roles.py` (templates carry no `nhms` credential in any form — `nhms:` DSN or `PGUSER=nhms` — except the two allow-listed lanes; SQL names exactly the template roles; SQL ownership loop covers the six schemas; ingest default-privilege block and display-audit clause present; SQL grants ⊇ scanned `met.*` targets for download; forbidden statements absent: `REASSIGN OWNED`, `GRANT nhms TO`, single-transaction `DO` around the ownership loop).
- Storage/cache/query: ownership/grants in the catalog; `ALTER DEFAULT PRIVILEGES`; tablespace `CREATE` grant.
- Public routes/entrypoints: six env files (ingest, download, compression, cold-residency, retention, replay-exception); `scripts/node27_provision_write_roles.sh`.
- Frontend/downstream consumers: none (display stays on `nhms_display_ro`).
- Failure paths/rollback/stale state: a missing privilege surfaces as `permission denied` in the unit's journal (+ `OnFailure` where present) or as a `warning` stats-guard entry; rollback by env restore; new migration tables are owned by `nhms` until re-provision (audit-visible) but remain writable via default privileges; a lock-timeout during the ownership loop is retried per relation (autocommit), so the display API never waits longer than one relation's `lock_timeout`; exhaustion = partial transfer reported by the audit, cutover blocked.
- Evidence/audit/readiness: pre-merge role/probe receipts incl. both stats-guard legs `ok` in the dry tick; post-merge per-unit receipts; `pg_roles` output; redacted `grep` of env files.
- Regression rows:
  - provision script run twice -> identical audit output, no error; run after a migration that adds `hydro.newtab` -> ingest INSERT into `hydro.newtab` succeeds during the window (default privileges), only its ANALYZE entry is `warning`, audit reports the owner drift, re-run fixes it.
  - `nhms_ingest_rw`: `compress_chunk`/`drop_chunks`/chunk `ANALYZE`/authority-table `ANALYZE`/`SET TABLESPACE nhms_cold` succeed; `COPY … FROM PROGRAM` -> `must be superuser`; `CREATE ROLE`/`CREATE DATABASE` -> denied.
  - `nhms_download_rw`: INSERT into a `met.*` table succeeds (privilege-shape probe, not a lane path); `compress_chunk` -> `must be owner`; `COPY … FROM PROGRAM` denied.
  - unchanged sibling: `nhms_display_ro` `SELECT` set identical before/after (audit query + `relacl` capture); drill and replay envs keep `nhms`; migrations still run as `nhms`; display API unaffected.

## Boundary surfaces

Auth surface: role creation/grants/ownership (DDL on production, pre-approved by the user) inside a timer-stopped window. Config: six env files + templates. Publish/rollback: env cutover per unit with `*.env.pre-1774` backups. Unchanged downstream: display role, migration role, schemas, replay and drill lanes.
