Pinned on real PostgreSQL by `tests/test_node27_ingest_run.py::test_register_upsert_renews_updated_at_of_a_failed_run_without_touching_its_failure`. An abandoned historical failure is not a residency signal and would otherwise alert every 24 h forever the moment the lane is enabled — the uncleareable-daily-mail shape #2464 fixes; the 2 rows above stay outside the watched set (recorded in §Stated consequences). A retried run never passes through an intermediate status: it stays `failed` (register keeps it, `mark_run_failed` no-ops) until `mark_run_parsed` moves it to `parsed`. State file (JSON, atomic replace, `fcntl` lock — copy `scripts/node27_frontier_stall_alert.py`'s state/lock shape): `{run_id: {first_observed_failing_at, last_alerted_at}}`; runs no longer failing are dropped. - D6 (#2504) window-aware guard. Resolver `configured_retention_window_days(env) -> int | None` in `packages/common/storage.py`: parses `NODE27_TIMESERIES_RETENTION_WINDOW_DAYS` and returns `None` when it is absent or unparseable/non-positive. The retention runner uses it and keeps its OWN existing default and typed validation errors (behaviour unchanged). The coverage refresh is **fail-closed**: `None` → no relaxation at all and an empty expired selection (today's behaviour byte-for-byte). Reason: the refresh runs from `scripts/node27_autopipe_cron.sh`, which sources `infra/env/node27-ingest.env` — measured on node-27 today, that file does NOT carry the window variable (it lives in `node27-timeseries-retention.env`, live value 21); falling back to `DEFAULT_RETENTION_WINDOW_DAYS = 14` would relax the guard for the 14–21-day band whose chunks retention has not dropped, violating the in-window must-preserve (and pre-empting batch G2's #2457 in-window decision). The variable is added to `infra/env/node27-ingest.example` with a comment that it MUST equal the retention env's value; setting it on node-27 is the operator's deployment step. The cron's strict-source filter only rejects libpq `PG*` keys (verified), so the new key passes it. Guard becomes `WHERE force OR EXCLUDED.segment_count > 0 OR current.segment_count = 0 OR current.river_valid_time_end < :expired_cutoff` with `expired_cutoff = display_watermark - window`, where `display_watermark` comes from `packages/common/display_watermark.py::fetch_display_watermark` — the SAME anchor the retention runner uses (`reference_time`), never wall time (that module forbids a wall-time fallback; with a lagging watermark, `now() - window` would declare a band expired that retention has not dropped). A watermark error → no relaxation and an empty expired selection (fail-closed); the `--all` path fetches the watermark once per batch, not per run (a stored end older than the cutoff is the only relaxation; NULL end never relaxes; window `None` → the relaxation term and the expired selection are omitted entirely). `--skip-fresh` selection additionally includes `segment_count > 0 AND river_valid_time_end < :expired_cutoff AND refreshed_at < now() - <expired_rescan_interval>` (default 24 h): facts routinely outlive the cutoff (1-day chunk granularity, refused/deferred retention ticks such as 09-19's 55P03), and without the bound an expired row whose facts survive would be fully rescanned on every ~11-min autopipe tick, serially under the autopipe flock (`--workers ${AUTOPIPE_COVERAGE_WORKERS:-1}`), each up to the refresh statement budget. Because the refresh rescans actual facts, a row whose chunk is not yet dropped keeps its count. Audit: `scripts/node27_refresh_coverage.py --audit-populated-empty` (read-only; bounded per-run `EXISTS` probe restricted to the row's stored valid-time range; autocommit / one short transaction per probe, `statement_timeout` AND `lock_timeout` set, so no AccessShare lock is held across chunks to block `drop_chunk` — the #2355 comment attributes 09-19's retention 55P03 refusal to exactly such a manual probe). NULL-end populated rows are reported in their own bucket `null_end` and stay frozen (never relaxed) printing `{in_window: {total, empty}, out_of_window: {total, empty}, null_end: {total}, watermark, cutoff}` JSON; exit 0 always unless DB error (exit 2). Header argument and `_REFUSAL_ADVICE` rewritten: in-window refusal = investigate (legacy cohort / anomalous loss), out-of-window zero = expected convergence. Rationale for narrowing #1446 (write into the header and PR body; it is an explicit reinterpretation of #2504 AC2, which is satisfied by the in-window legacy-cohort test in 6.3): after migration 000060 no column distinguishes legacy-routed from narrow-routed runs and no display path reads `hydro.river_timeseries_legacy` (dropped), so outside the window every cohort's vanished facts are equally gone and a populated row only advertises an empty curve.

## Stated consequences (PR body)

- D5 exit 2 (config/DB/state error) is non-zero, so `OnFailure=` mails on every 30-min tick while the observer is broken, undeduped. Intended: a broken observer is operator-actionable; same posture as the coverage-freshness lane.
- First `--all --skip-fresh` after the window variable is set on node-27 rescans the expired populated rows once: 2666 out-of-window populated rows, 2616 of them empty, on the committed 6.5 read-only audit (`docs/runbooks/receipts/2026-09-23-issue-2504-populated-empty-audit/README.md`; window 21, watermark 2026-09-22T12:00Z; the audit's own serial probe pass over 6755 rows took 101 s). Run on the backstop, that first pass would run under the autopipe flock (`--workers ${AUTOPIPE_COVERAGE_WORKERS:-1}`, live 2 per `service-bringup.md`), delaying the next tick for as long as the rescans take; the runbook's deployment step (`docs/runbooks/production-ops/service-bringup.md`, #2504 bullets) therefore runs the first convergence once by hand, OUTSIDE the flock and with the window set inline, BEFORE the window is written into `node27-ingest.env` — the backstop then only sees rows refreshed within the last 24 h and does not reselect them. The empty ones become 0 and leave the selection. Steady state: rows crossing the cutoff each day, plus expired rows whose facts still survive (chunk not yet dropped), each re-selected at most once per `expired_rescan_interval` (24 h).
- Retention-stall residual: if retention is disabled or refused for days (09-19's 55P03 shape, or the timer stopped), expired rows whose facts survive accumulate, and each is rescanned once per 24 h under the autopipe flock; the backstop's `phase=coverage_backstop elapsed_sec=` line in `autopipe.log` grows with that set. The runbook tells the operator to watch that line (and the retention receipts) whenever retention has not dropped chunks for more than a day.
- D6 also lowers the out-of-window rows of the legacy-routed 000060 cohort (which #2504 fenced out of scope as a cause); they are included because after 000060 they are indistinguishable and equally empty — stated explicitly in the PR body.
- #2529 observer ignores the 2 abandoned `OUTPUT_PARSE_COMPRESSED_CHUNK_BLOCKED` rows from 2026-08-28 (not retried for 26 days); clearing them is an operator reparse/mark action documented in the runbook, not an alert.
- #2529 claimed blind spot — the recompute path: a `published` run whose product is rewritten (warm-start rewrite of the same `run_id`) is re-registered every tick and re-parsed; if that re-parse fails deterministically, `mark_run_failed` no-ops (`FAILABLE_RUN_STATUSES` excludes `published`), `parsed_at` stays old, and the tick exits rc=1 forever while the status never becomes `failed` — outside this lane's `status='failed'` set, and outside the frontier lane (the cycle is already covered). A DB-only predicate (`status='published' AND updated_at > floor AND parsed_at < updated_at`) would also catch the forcing-stage legacy-store-refused `skipped` recompute, so it needs its own design decision; tracked as a follow-up issue, not closed here.
- #2529 widening residual: a `failed` run whose forcing version is legacy-routed is re-registered (renewing `updated_at`) and then `skipped` at `REASON_APPLY_LEGACY_STORE_REFUSED` before the parser, so it stays resident and mails every 24 h until task 8.2's legacy-cohort handling; zero such rows today (6b). Same exposure existed under the first prefix cut for `OUTPUT_PARSE_*` codes.
- The new timer is NOT enabled by this PR, unlike the coverage-freshness/frontier lanes (both enabled on node-27): the deployed checkout `/home/nwm/NWM` is behind master and would not contain the script; enabling is part of the next node-27 deployment (deliberate deviation from lane convention, recorded).
