# File-journal read-blocked consumers and the file lane's public URI evidence

## Why

`_blocked_query_job` (`services/orchestrator/file_orchestration_journal.py:13693`) is the journal's single synthetic row for "this read was refused": PRESENT, non-terminal, `status == file_journal_read_blocked`, and marked by `file_journal = {status: "blocked", reason, field, evidence}`. Five query entrypoints return it (`:1984`, `:2000`, `:2112`, `:2145`, `:2153`). Guards that key on the marker fail closed correctly (`submission_runtime_root_resolution` `:12173`, `operator_released_reservation_recovery.py:52`; `pipeline_job_provenance.py:698` keys on the status literal instead because its publication projection drops `file_journal` entirely). Three retry-lane consumers never learned the marker, and one unrelated write-boundary interaction nulls the file lane's URI evidence (batch E1, one PR at the user's request):

- **#2385** — `_manual_retry_source_for_run` (`:12377`) is the only consumer that **discards** the sentinel, by comparing `job_id` (`:12380`). The by-run lane mints the row with the real `run_id` and the default `job_id`, so the filter deletes it, `safe_jobs` is empty, and both callers (`:11523`, `:11622`) raise `RetryNotFoundError` → **404 `RETRY_NOT_FOUND` "No retryable failure found for this run."** A refused read is reported as "this run has nothing to retry". The same function's `_hydro_run_for` (`:12383`) has no `except`, so a fault that also hits the cycle replay escapes untyped (500).
- **#2387** — `_retry_job_for_stage_result` (`chain_forecast_execution.py:793`) builds a `PipelineJob` straight off `get_pipeline_job`'s blocked row, so `error_code` becomes the journal's refusal reason and `should_auto_retry` classifies a retryable `SLURM_TIMEOUT` job as non-transient → `mark_permanently_failed`. Today the identity sanitizer inside `_file_retry_job_record` raises first (`run_id=None` → `file_journal_unsafe_identity`), so there is no dirty write — but that is an accident of the by-id lane leaving `run_id`/`cycle_id` empty; the issue's counterfactual probe shows the by-run/by-cycle row shape persists `permanently_failed` with the journal reason as the error code. `_file_retry_event_runtime_root_candidates` (`:12206`) and `_file_retry_previous_job_id` (`:12086`) call `_source_id_from_job` on the same row, which raises `file_journal_missing_identity`.
  - **The issue's "unclassified 500" for that second half is stale on this tree and the real defect is worse.** The provenance walk runs inside `attempt_manual_retry`'s `except Exception` (`:11829-11838`), after the pending retry row has been minted. A refused predecessor read is therefore caught, `_retry_submission_error_code` (`retry.py:1274`) finds no `.code` on `FileOrchestrationJournalError` and returns `SBATCH_SUBMISSION_FAILED`, and `_record_manual_retry_submission_failure` (`:12356`) **persists the fresh pending retry row as `submission_failed`** with a fabricated gateway error code and a derived `file_journal_missing_identity` message. The route then answers a structured 503 that blames the gateway for a journal read the operator can neither see nor act on.
- **#2306** — the file lane's manual-retry submission events pre-render their evidence (`_manual_retry_submission_failure_details` `:13195`/`:13197`) **before** `insert_pipeline_event`. The caller-boundary anti-laundering strip (`_append_validated_record_unlocked` `:9998` → `_strip_redaction_placeholders`) then sees the journal's own deliberate `[object-uri]`/`[uri]` output and replaces it with `null`, so a URI-shaped runtime root reaches the 503 as `present: true, value: null` while the database lane sends `[object-uri]`/`[uri]`. `_journal_record_for_write` already states the governing principle — the strip removes placeholders that came FROM A CALLER and must never run downstream of the journal's own public rendering — and this writer is the one caller that violates it.

#2385 and #2387 are two consumer ends of one sentinel family: they are fixed in a single pass behind one discriminator so neither overwrites the other's assumption about the row.

## What Changes

- One shape-keyed discriminator on the journal module next to `_blocked_query_job`: a row is blocked when `file_journal.status == "blocked"`. `job_id` comparison stops being a discriminator anywhere. `_blocked_query_job`'s row shape is **unchanged** (fields, defaults, marker, reason token, non-terminal status); only its docstring's dependent list is rewritten to name the marker instead of the deleted `job_id` filter.
- #2385: `_manual_retry_source_for_run` detects the blocked row before building `safe_jobs` and raises the existing `RetryEvidenceInvalidError(run_id, reason, field)` → **409 `RETRY_EVIDENCE_INVALID`** carrying `journal_reason`/`journal_field`; the same translation wraps `_hydro_run_for`. The now-dead `job_id` filter is deleted. "Genuinely no jobs" still returns 404; active still returns 409 `RETRY_CONFLICT`. The selector's third caller, the node-22 operator script `scripts/node22_manual_retry_failed_runs.py:52`, catches the new refusal and reports it as a receipt entry (`reason: journal_read_blocked`) instead of dying on an uncaught exception outside `main()`'s try (`:100`).
- #2387: `_retry_job_for_stage_result` refuses a blocked record with `OrchestratorError("FILE_JOURNAL_READ_BLOCKED", ...)` carrying the journal reason/field (the repo's own precedent at `:1949`/`:1970`), never `None` — `None` would make `_schedule_cycle_stage_retry` read "do not retry" with no signal. `_file_retry_event_runtime_root_candidates` and `_file_retry_previous_job_id` degrade like their sibling at `:12173`: empty batch / `None` plus a `LOGGER.warning` with reason and field. The walk then continues on the remaining candidates, so a recorded `submission_failed` — if one still happens — carries the runtime-root lane's own code instead of a fabricated `SBATCH_SUBMISSION_FAILED` blamed on a gateway that was never called.
- #2306: the file lane stops pre-rendering. `_manual_retry_submission_failure_details` (failure event) and the sibling success-submission writer (`:12332`) hand `insert_pipeline_event` the secrets-redacted-but-unrendered mapping; the caller-boundary strip then sees no placeholder to null, and `_public_pipeline_event_payload` (`:12507`) renders the whole `details` tree exactly once. The durable event ends up carrying `[object-uri]`/`[uri]` instead of `null`, the DB lane's wire shape, with no raw root persisted in the public event and `submission_runtime_root_resolution` unchanged ("response equals persisted" preserved).

### Modified Capabilities

## Impact

- Code: `services/orchestrator/file_orchestration_journal.py` (discriminator, three consumers, two event writers, one docstring), `services/orchestrator/chain_forecast_execution.py` (`_retry_job_for_stage_result`), `scripts/node22_manual_retry_failed_runs.py` (`_preview` refusal shape).

- Docs: none (no runbook states these behaviours).
- Runtime: node-22's db-free retry lane (compute/Slurm/artifact producer only; active DB writes and ingest validation stay on node-27) and the `POST /api/v1/runs/{run_id}/retry` route served from node-27. No schema or migration. Batch E2 (#2308) shares `retry.py` / `apps/api/routes/pipeline.py` with this change and starts only after this PR merges.
