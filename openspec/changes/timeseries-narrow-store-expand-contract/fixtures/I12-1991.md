**The rc = 0 half does transfer, and must not be dropped.** `packages/common/forcing_domain_handoff_apply.py`

### E5 — `EXISTS` is not a per-version probe at production scale; the shipped SQL was not the SQL that was measured

**Falsified on the node-27 oracle, 2026-09-19, read-only, after this fixture's own first revision
shipped.** The "routing backfill's oracle" paragraph under the migration contract below prescribed
`EXISTS (SELECT 1 FROM …_legacy WHERE forcing_version_id = fv.forcing_version_id)` and asserted it
is "a PK-leading probe per version — cheap per row". On the live data it is not. (That paragraph
now carries the corrected spelling; it is referred to here by name rather than by line number,
because this very edit moved it.)
PostgreSQL's `pull_up_sublinks` flattens an `EXISTS` sublink in `WHERE` into a semi-join, and on
8 881 versions against a 77 GB / 226M-row / 6-chunk fact table the planner chooses to build the
distinct side from the **fact table**, not to probe it:

```
Aggregate  (cost=10328441.17..10328441.18)
  -> Nested Loop
       -> HashAggregate  (cost=10328438.53..10328438.54)  Group Key: legacy_1.forcing_version_id
            -> Append  (cost=0.14..8233001.37 rows=838174864)
                 Custom Scan (DecompressChunk) on _hyper_1_87_chunk
                 Custom Scan (DecompressChunk) on _hyper_1_106_chunk
                 Seq Scan on _hyper_1_109_chunk  (rows=65234261)
                 Seq Scan on _hyper_1_112_chunk  (rows=47209111)
                 …
       -> Index Only Scan using forcing_version_pkey on forcing_version fv
```

Both compressed chunks are decompressed and the whole table is hash-aggregated. **This plan was
not executed** — production was not stressed to confirm a plan that is being replaced; it is
rejected on shape and cost.

**The decisive evidence is that the header's own budget cites a measurement of a query the
flattening transform never applied to.** Sharpened by the implementer against the receipt's own
SQL — `receipts/2026-09-18-i10-forcing-readonly/existence-probe.sql` runs

```sql
SELECT fv.forcing_version_id,
       EXISTS (SELECT 1 FROM met.forcing_station_timeseries f
                WHERE f.forcing_version_id = fv.forcing_version_id) AS has_legacy_rows
  FROM met.forcing_version fv;
```

— the `EXISTS` is in the **target list**, not a `WHERE` qual. `pull_up_sublinks` only pulls up
sublinks sitting in `WHERE`/`JOIN` quals, so there it stays a `SubPlan` and runs as the
per-version probe. So §4's 21 849 ms / 238 ms was **never applicable to a `WHERE EXISTS`** — the
defect is not "a different shape was measured" but "the sublink was measured in the one syntactic
position where the transform does not fire". Measuring the probe form today, this time in the
`WHERE` position that step 11 actually needs, reproduces §4's warm figure **exactly**:

```
SELECT count(*) FROM met.forcing_version fv
WHERE (SELECT 1 FROM met.forcing_station_timeseries legacy
       WHERE legacy.forcing_version_id = fv.forcing_version_id LIMIT 1) IS NOT NULL;
-> Planning Time: 7.670 ms   Execution Time: 238.017 ms
```

Ruling: **step 11 ships the scalar-subquery form**, which makes the delivered SQL the SQL that
was measured. The rewrite is semantically identical (the subquery projects the constant `1`, so
it is one row or no row; `IS NOT NULL` is true iff a row exists) and the fix is **structural, not
a lucky plan choice**: `pull_up_sublinks` does not flatten a scalar sublink, and because it is
correlated it cannot become a hashed SubPlan either. That is why the repair is a rewrite and not
`SET LOCAL enable_hashagg = off` — by the time that GUC is consulted the flattening has already
happened, so it only bans one way of executing the semi-join and leaves the shape to the cost
model on whatever chunk constitution exists on install day.

**`LIMIT 1` is correctness, not tuning, and dropping it breaks the migration outright.** Found by
the implementer, verified on production read-only:

```
SELECT count(*) FROM met.forcing_version fv
WHERE (SELECT 1 FROM met.forcing_station_timeseries l
       WHERE l.forcing_version_id = fv.forcing_version_id) IS NOT NULL;
ERROR:  more than one row returned by a subquery used as an expression
```

Every version with legacy rows has thousands of them, so without the `LIMIT` the `UPDATE` fails on
the first of the 4 289 — it does not merely run slower. A later editor "simplifying" the predicate
must not drop it.

Why no oracle caught it: CI's dry run is `pg15-latest` with seed-sized data, where either form is
instant — planner behaviour at 77 GB is invisible there. Same class as the I12 P1 (green CI, no
oracle that could see it), and the reason 8.1 measures on node-27 **before** the window rather
than reporting after it.

Measured inputs, all 2026-09-19, read-only: 8 881 versions; fact table 77 GB, ~226M rows,
6 chunks, 2 compressed; compression `segmentby (forcing_version_id, station_id)`, which is what
gives the compressed chunks a usable index for the probe; classification result
**4 289 `legacy` / 4 592 `narrow`**.

**The single-version probe figure does not extrapolate, and 8.1 must not extrapolate it.** One
version probed as its own statement measures 0.25 ms / 19 buffers, but that includes executor
startup and the six-chunk `Append` setup paid once per statement; inside the batch each `SubPlan`
invocation costs roughly 0.027 ms. Multiplying 0.25 ms by the version count gives ~2.2 s, about
9x the measured 238 ms. **238 ms for the whole predicate is the number the window plans against**;
0.25 ms is only evidence that a single probe is an index descent rather than a scan.

### Lock budget — measured, and the number to use is not the first one

The IDENTITY adds, not the routing backfill, are the largest lock event.
`ALTER TABLE … ADD COLUMN … INTEGER GENERATED ALWAYS AS IDENTITY UNIQUE` carries a volatile
default, so PostgreSQL **rewrites the whole table under `AccessExclusiveLock`** and then builds
the UNIQUE index. From `receipts/2026-09-18-i10-forcing-readonly/README.md:53-65`, on a
throwaway cluster:

| table | wall time | lock |
|---|---|---|
| `met.forcing_version` | **689 ms** | `AccessExclusiveLock` |
| `met.met_station`, live **data** constitution | **1 141 ms** | `AccessExclusiveLock` |
| `met.met_station`, live **page** constitution | **1 863 ms** | `AccessExclusiveLock` |

`met.met_station` is joined by every narrow reader and read by the display API on the active
primary. **`identity.out`'s numbers (734 ms / 625 ms) are a first attempt and must not be used**
(same receipt, `:71`). Which `met_station` row applies depends on the live heap's constitution at
window time; that is 8.1's measurement, not 7.3's — but the fixture records both bounds so the
IDENTITY step is planned against 1 863 ms, not 1 141 ms.

**The IDENTITY adds are not the whole window, and the first revision of this section implied
they were.** Corrected on review: the routing backfill's own cost is measured in §4 of the same
receipt (`:82-96`) — the per-`forcing_version` probe over all 8 653 versions *as they stood then*
runs **21 849 ms cold / 238 ms warm**; the population is 8 881 as of 2026-09-19 and the warm
figure reproduced exactly (E5). The migration is a single `DO $$` block and therefore a single
implicit transaction (there is no `BEGIN`/`COMMIT` to find), so the `AccessExclusiveLock` the
step-3 RENAME takes on the fact table is held until the step-11 backfill commits. The window to
plan is therefore the **sum**:

| component | cold | warm |
|---|---|---|
| IDENTITY rewrites (`met_station` page constitution + `forcing_version`) | ~2 552 ms | — |
| step 11 `ADD COLUMN timeseries_store … DEFAULT 'narrow'` | catalog-only | catalog-only |
| step 11 `UPDATE` predicate = the §4 probe, now the shape actually shipped | **21 849 ms** (8 653 versions, 2026-09-18) | **238 ms** (8 881 versions, 2026-09-19) |
| **total AccessExclusiveLock window** | **~24 s** | **~3 s** |
