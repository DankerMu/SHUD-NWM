(`design.md:126`, `specs/forcing-narrow-store/spec.md` Requirement "Forcing readers SHALL
render per-store variants like the river readers", `tasks.md` 7.2a and 7.2) are the

then withdrawn on evidence — kept visible rather than deleted).

Third revision. Round 1's P0 was answered by the deployability decision (D1) below, which
changed the shape of the whole issue. Round 2 caught three written contradictions with D1
and one claim of mine that was simply false; all four are corrected here, and the false one
is retracted in place rather than quietly removed.

## D1 — the deployability decision (answers the first review's P0)

**The trap.** The obvious reading of this issue is river's: register a `legacy` template
that targets `met.forcing_station_timeseries_legacy` and a `narrow` one that targets the
canonical name, wire the nine readers, and let 7.3's expand migration create both. Under
that reading, between I11's merge and 7.3 every production forcing read points at a
relation that **does not exist**. That is not a test-only concern: per `CLAUDE.md`'s
standard loop node-27 pulls master and runs real-DB pytest, and node-27 is the active
primary behind `https://test.nwm.ac.cn`.

**River really did do that, and it is not a precedent to copy.** Verified, not assumed:

| commit | date | what |
|---|---|---|
| `e8b30893c` | 2026-09-09 | river readers wired, `_qhh_latest_timeseries_store` introduced |
| `8a61f5347` | 2026-09-12 | `000059` creates `hydro_run.timeseries_store` **and** renames the table |

`_qhh_latest_timeseries_store` raises `TIMESERIES_STORE_INVALID` (HTTP 500) when the column
is absent, so for those three days master was **fail-closed undeployable** and the gate was
"nobody deploy". River got away with it. Repeating it on the forcing side is a worse bet:
the forcing readers include the display-coverage refresh, which runs on node-27's ingest
path against the deployed schema.

**Correction (cut (b) review).** An earlier revision of this line also named "the
station-series API that `test.nwm.ac.cn` serves". That is wrong:
`PsycopgForecastStore.station_series` has **no production caller** —
`apps/api/routes/data_sources.py:140` serves `/met/stations/{id}/series` through
`read_station_forcing_csv`, the object-store direct read (`docs/runbooks/
object-store-forcing-series-read.md`), and a repo-wide grep for `.station_series(` over
`apps/ services/ packages/ workers/ scripts/` is empty. D1's argument stands on the
display-coverage refresh alone and does not need the API; but see the verification gap
recorded under reader #3 below, which this same fact opens.

**Decision: the table names are transitional constants, not fixed template text.**

```text
I11:  FORCING_TABLE        = "met.forcing_station_timeseries"   # future narrow name; never rendered (store is constant legacy)
      FORCING_TABLE_LEGACY = "met.forcing_station_timeseries"   # the table that exists today
7.3:  FORCING_TABLE_LEGACY = "met.forcing_station_timeseries_legacy"   # one line, in the migration's own commit
```

Consequences, all of them good:

- **every commit on master stays deployable.** Never break userspace.
- I11 becomes a genuinely zero-behaviour-change refactor, which upgrades M1 from
  "semantically identical" to **byte-identical rendered SQL** for eight of the nine
  readers — the strongest pin available, and one that only this decision makes reachable.
- the `_legacy` flip lands in the same commit as the migration that makes it true.

This is a **deliberate improvement over river's shape, not a precedent**. `tasks.md` 7.3
is amended to carry the constant flip as part of the migration commit. The spec's `_legacy`
wording describes the post-7.3 end state and is unchanged.

**What this does not buy.** Nothing here makes I11 provable at the row level; C1 still
holds. And the narrow variant is unrendered dead text until 7.3 — that is accepted, it is
what "store is constant legacy" means, and I1–I5 pin its shape textually in the meantime.

### C4 — display-coverage's forcing leg is a single render, not a two-store union

(A shape point, not a routing point. Every reader is legacy-only in I11 because store is
constant `legacy`; what is special about display-coverage is that its *final* form cannot
be a per-call render at all.)

`_COVERAGE_CTES` (`packages/common/display_coverage.py:197-559`) and `_REFRESH_SQL`
(`:585`) are **module-level constants built at import time**. River's answer is
`_RIVER_SAMPLE_ROWS_UNION_SQL` (`:191-194`): a static two-store `UNION ALL` of both renders,
joined once at import. Per-version routing happens in the data, not in Python.

The forcing leg cannot do that in I11: the narrow branch would have to reference
`fv.timeseries_store` and narrow columns that do not exist, at **import time**, in every
process that imports the module — including the display API on node-27.

**Decision: I11 renders display-coverage's forcing leg through the renderer with the
`legacy` variant only — a single render, no union. The static two-store `UNION ALL` lands in
7.3, with the column.** This keeps D1's property (import-time SQL is always runnable) and
leaves the reader registered. (Its per-file mention count then drops 1→0 once D1's constants replace the literal name — by design; see the execution split.)

### C5 — WITHDRAWN: the readiness-counter divergence I claimed does not exist

The second revision of this fixture asserted that legacy's `unit` and `quality_flag` are
nullable text, that the narrow table's `NOT NULL` enums therefore force
`missing_unit_samples` / `missing_quality_flag_samples` to 0 on one side only, and that the
spec might need a MODIFIED clause. **That premise is false and the conclusion with it.**

```
db/migrations/000005_met.sql:107:  unit TEXT NOT NULL,
db/migrations/000005_met.sql:109:  quality_flag TEXT NOT NULL DEFAULT 'ok',
```

No migration alters either column; there is no `DROP NOT NULL` anywhere in `db/migrations/`.
Both columns are already `NOT NULL`, so in
`_fetch_forcing_readiness_variable_rows` (`packages/common/forecast_store.py:2796-2800`)
the `unit IS NULL` / `quality_flag IS NULL` branches are dead on **both** stores and each
counter reduces to the blank-string branch, `BTRIM(...) = ''`.

Whether that branch can fire is a data question, and I10 already measured it:
`design.md:181` records the production domain as `unit` 6 values in strict 1:1 with
`variable`, and `quality_flag` a single value `ok`. No blank or whitespace-only label. So
both counters are **0 on both stores today**, and the three-source enum union
(`design.md:126`) covers every observed label.

**Nothing is deferred and no spec decision is needed.** The only residual is already in
7.3's own design: the enum union must be built so that a label the census never saw fails
the migration loudly rather than silently dropping rows. `tasks.md` 7.3 is corrected to
remove the spurious "a spec decision is required before implementing".

Recorded rather than deleted because the contract file carried the false claim for a
revision and the next reader deserves to know it was retracted on evidence, not quietly
dropped.

## Renderer shape — what to reuse from river and what not to

`render_river_ts_sql(template, store, *, entry)` (`packages/common/river_ts_render.py:2614`)
is a **single-template line-deletion transform**: `legacy` renames the table
(`_rename_table`, `:2424`, canonical → `_legacy`) and keeps the transitional-aid conjuncts;
`narrow` strips every `-- … remove with #1342` marker line and its conjunct. That machinery
exists because the legacy **river** table has key columns.

The legacy **forcing** table has none — its PK is
`(forcing_version_id, station_id, variable, valid_time)`, all text
(`db/migrations/000005_met.sql`). **Do not port the line-deletion logic.**
`render_forcing_ts_sql(template_pair, store)` holds two independently registered template
strings per reader and selects one (`design.md:126`). Table names come from the two module
constants in D1, not from literal text inside the templates — that is what makes the 7.3
flip a one-line change and what lets the census see exactly two qualified mentions in the
renderer module.

What *is* reusable is the **test-side registry dataclass**:
`TemplateEntry(key, path, kind, params, expected_aids, mentions, source: Callable[[str], str])`
(`tests/river_ts_template_registry.py:122-146`) — `source(store)` already takes the store
string. Mirror it as `tests/forcing_ts_template_registry.py` and drop `expected_aids`
(no markers). Mirror the census machinery too, with the C3 traps budgeted.
