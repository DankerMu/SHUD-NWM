## D5 锁面（实测，非推理）

在本地同版本容器上，`through="000059"` + seed 后于**未提交的事务内**执行
`DROP TABLE hydro.river_timeseries_legacy`，随即查本会话持有的锁：

```sql
SELECT c.relname, l.mode FROM pg_locks l
  JOIN pg_class c ON c.oid = l.relation
  JOIN pg_namespace n ON n.oid = c.relnamespace
 WHERE l.pid = pg_backend_pid() AND l.mode = 'AccessExclusiveLock'
   AND n.nspname IN ('hydro','core')
   AND c.relname NOT LIKE '_hyper%' AND c.relname NOT LIKE 'compress_hyper%';
-- ('river_segment', 'AccessExclusiveLock')
```

**`core.river_segment` 被 ACCESS EXCLUSIVE 锁住**，由块内**第一条** DDL 取得，持到 COMMIT。
它是 MVT / `/river-segments` / `/forecast-series` 共同的读表。

加上 `lock_timeout` 只约束**等锁**不约束**持锁**、而 717 GB 的文件 unlink 发生在 COMMIT 内
（`statement_timeout` 默认不设且不覆盖 commit 阶段），结论是：
**本迁移必须在停掉 API 与 parser unit 的维护窗口内执行**。原注释宣称的
"最坏等 5 秒、否则干净回滚" 是错误的安全感——回滚确实安全，但那是"可安全中止"，不是"可带流量执行"。

### 执行前必补（不阻断合并，阻断执行）

   ```sql
   SELECT count(*) FROM hydro.hydro_run h
   WHERE h.end_time >= '2026-08-27 00:00+00'
     AND NOT EXISTS (SELECT 1 FROM hydro.river_timeseries t WHERE t.run_key = h.run_key);
   ```

   为 0 即证明"凡可能在残留 chunk 里有事实的 run，窄表都有它的事实"。
